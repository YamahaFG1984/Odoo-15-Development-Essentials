第 14 章

内置模型

新建一个数据库时，即使一个应用都不装，里面也已经有几百个模型：联系人、用户、公司、菜单、视图、动作…… 我们在前面的章节里一直在使用它们（比如 res.partner、ir.ui.view），这一章换个角度， 把它们摊开来看：每个模型存什么、彼此怎么关联，以及在哪个菜单里能看到它们。

本章目标

  • 看懂模型名前缀 res.、ir.、mail. 的含义
  • 掌握联系人、用户、公司这组「主数据」模型的关系
  • 认识描述「Odoo 自身」的信息仓库模型：安全、数据库结构、界面元素
  • 了解系统参数、默认值和公司相关字段在 Odoo 20 里如何存储
  • 理解消息、关注者、活动背后的数据模型

先看懂模型名的前缀

Odoo 的模型名通常是 前缀.名字 的形式，前缀告诉你它属于哪一类：

要查看这些模型，先打开开发者模式（第 1 章），然后进入 设置 → 技术（Settings → Technical）菜单。 本章出现的大部分模型都在这里有对应的菜单项。

怎么读本章的关系图

本章用简化的实体关系图（ERD）表示模型之间的关系，约定如下：

联系人数据模型

联系人（res.partner）是 Odoo 里最核心的模型之一：凡是需要表示一个人、一个组织或一个地址的地方都用它。 客户、供应商、联系人、发票地址、送货地址都是 partner；用户和公司的姓名、邮箱、地址也存放在各自关联的 partner 上。 这个模型由 base 模块提供，但相关菜单要安装「联系人」（Contacts）应用后才出现。

模型说明在哪里看
res.partner联系人。is_company 区分个人和公司，parent_id 指向所属公司，commercial_partner_id 算出「真正做生意的那个实体」联系人应用
res.partner.category联系人标签，可以有层级联系人 → 配置 → 标签
res.partner.industry行业分类（预置了欧盟 NACE 分类）联系人 → 配置 → 行业
res.partner.bank银行账户，属于某个联系人联系人 → 配置 → 银行账户
res.country国家：ISO 代码、电话区号、货币、地址格式。新建数据库时自动填好联系人 → 配置 → 本地化 → 国家
res.country.state省、州等行政区… → 本地化 → 省/州
res.country.group国家分组，比如「欧洲」，用于税、价格表等规则… → 本地化 → 国家组
res.currency货币。预置了全部货币，用到的需要激活开票 / 会计 → 配置 → 货币
⇪ Odoo 20 变化

书中的「银行」模型 res.bank 在 Odoo 20 已经不存在了：银行名称、BIC（SWIFT 代码）和地址直接存放在银行账户 res.partner.bank 的 bank_name、bank_bic 等字段上，不再需要先维护一份「银行」清单。

用户与公司数据模型

用户和公司在 设置 → 用户和公司 菜单里管理。它们都有一个隐藏的「影子」联系人：

  • 用户 res.users：登录 Odoo 的账号。它用第 4 章讲过的委托继承（_inherits）关联 res.partner， 所以 user.name、user.email 其实读的是对应联系人的字段。
  • 公司 res.company：组织本身和与公司相关的配置（货币、Logo、报表抬头等）。新数据库自带一家公司，XML ID 是 base.main_company。 公司可以通过 parent_id 组成「总公司 – 分支机构」层级。
  • 权限组 res.groups：用户属于若干个组，从组获得权限。只有在开发者模式下才能看到「组」菜单。
为什么用户背后要有一个联系人？

因为很多地方只关心「一个人」，不关心他是不是能登录：消息的作者、文档的关注者、被 @ 的人都是 partner。 这样内部用户、门户用户、完全不登录的外部联系人可以用同一种方式处理。第 13 章的门户用户就是从联系人「升级」来的。

访问安全相关模型

用户通过权限组获得对功能和数据的访问权。在 Odoo 20 里，相关模型在 设置 → 技术 → 安全（需开发者模式）下：

模型说明菜单
res.groups权限组。implied_ids 表示「属于本组就自动属于那些组」，比如「图书馆经理」包含「图书馆用户」设置 → 用户和公司 → 组
res.groups.privilege把同一应用的几个组归为一项「权限」，在用户表单上显示为一个下拉框（如「图书馆：用户 / 经理」）设置 → 技术 → 安全 → 权限
ir.access访问规则：组 + 模型 + 操作（c/r/u/d）+ 可选的域设置 → 技术 → 安全 → 访问权限
Odoo 15（书中）
res.groups
  ├─ ir.model.access   组对模型的 CRUD 权限
  └─ ir.rule           用域限制能操作哪些记录
Odoo 20
res.groups ── privilege_id ──> res.groups.privilege
  └─ ir.access         组 + 模型 + 操作 + 域，一条搞定
⇪ Odoo 20 变化

ir.model.access 和 ir.rule 合并为 ir.access（详见第 3 章）；组的分类从 category_id 改为通过「权限」 res.groups.privilege 归类；字段改名：组的 users → user_ids，用户的 groups_id → group_ids。

数据库结构模型

ir. 开头的「信息仓库」模型描述的是 Odoo 自身：装了哪些模型、每个模型有哪些字段、每条数据的 XML ID 是什么。 它们在 设置 → 技术 → 数据库结构 和 设置 → 技术 → 序列与标识符 菜单下：

模型说明
ir.model已安装的每个模型一条记录，大多对应一张数据库表。「所属应用」字段列出参与定义它的模块
ir.model.fields每个字段一条记录。开发者菜单里的「查看字段」打开的就是它（书里写成了 ir.model.field，少了 s）
ir.model.constraint / ir.model.relation模块创建的数据库约束和多对多关系表，卸载模块时据此清理
ir.model.data外部标识符（XML ID）：把 library_app.book_odoo 这样的名字映射到具体数据库里的 id。菜单：技术 → 序列与标识符 → 外部标识符
ir.sequence自动编号规则，比如销售订单号 S00042
ir.attachment所有附件和二进制字段（图片等）统一存放的地方
decimal.precision小数精度配置，比如「产品价格保留 2 位小数」
「这条记录的 XML ID 是什么？」

打开任意一条记录，点开发者工具（虫子图标）→「数据」→「查看元数据」，能看到它的 XML ID、创建者、最后修改时间。 写继承视图时需要知道父视图的 XML ID，就用这个方法查。

界面相关模型

菜单、视图、动作也都是存在数据库里的记录——这正是我们在模块的 XML 文件里用 <record> 创建它们的原因。 它们在 设置 → 技术 → 用户界面 和 设置 → 技术 → 动作 下：

模型说明
ir.ui.menu菜单项，组成树形结构。叶子菜单通过 action 字段触发一个动作
ir.ui.view视图定义及其扩展：表单、列表、看板……以及 QWeb 模板（报表、网页都在这里）
ir.actions.actions所有动作类型的基础模型，一般不直接使用
ir.actions.act_window窗口动作，最常用：用一组视图（列表 + 表单……）展示某个模型
ir.actions.report报表动作（第 12 章）
ir.actions.server服务器动作：创建 / 修改记录、发消息、调用 Webhook、执行 Python 代码等
ir.actions.client客户端动作：打开一个前端注册的 OWL 组件（比如 Discuss 界面）
ir.cron定时任务：按计划执行一个服务器动作（设置 → 技术 → 自动化 → 计划的动作）
排查问题的好帮手

某个视图显示不对？到「技术 → 用户界面 → 视图」里按模型搜索，就能看到它的主视图和所有继承视图，以及每一个来自哪个模块。 这比在源代码里一个个 grep 快得多。

系统参数、默认值与公司相关字段

设置 → 技术 → 参数 菜单下有几个保存「配置」的模型：

  • 系统参数 ir.config_parameter：一个简单的「键 → 值」表，存全局配置。例如 web.base.url 保存服务器的公网地址， 邮件模板里生成链接时就用它。代码里这样读取：
ICP = self.env["ir.config_parameter"].sudo()
base_url = ICP.get_str("web.base.url")
batch_size = ICP.get_int("mail.batch_size", 50)   # 第二个参数是默认值
ICP.set_bool("my_module.feature_enabled", True)
⇪ Odoo 20 变化

书中（以及大量旧代码）使用的 get_param() / set_param() 在 Odoo 20 被按类型拆分的方法取代： get_str()、get_int()、get_float()、get_bool() 和对应的 set_*()， 取出来的值直接就是正确的 Python 类型，不用再自己转换。只想要服务器地址的话，记录上的 record.get_base_url() 更方便。

  • 默认值 ir.default：用户在界面上「设为默认值」或模块数据里设置的字段默认值，可以按用户、按公司区分。

公司相关字段（property 字段）

在多公司环境中，有些字段对同一条记录、在不同公司下需要有不同的值。比如同一个客户，在 A 公司记到「应收账款 1122」科目， 在 B 公司记到另一个科目。这种字段用 company_dependent=True 声明： 

property_account_receivable_id = fields.Many2one(
    "account.account",
    company_dependent=True,
)
⇪ Odoo 20 变化

书中讲的「公司属性」模型 ir.property 在 Odoo 18 被移除。现在公司相关字段直接存成模型表里的一个 jsonb 列（以公司 id 为键）， 读写、搜索都快得多；某公司没有值时的后备默认值存放在 ir.default。对开发者来说，声明方式 company_dependent=True 没变。

消息与活动数据模型

表单底部的「聊天器」（chatter）背后是 Discuss 应用（技术名 mail）提供的一组模型，相关菜单在 设置 → 技术 → 讨论 下。 第 8 章我们给借书单继承了 mail.thread 和 mail.activity.mixin，就是接入了这套模型：

模型说明
mail.message每一条消息：发送的邮件、内部备注、字段变更日志、系统通知
mail.message.subtype消息子类型。基本的有「备注」（内部）、「讨论」（对外）、「活动」；应用还可以定义自己的，比如「借书单已完成」
mail.followers某条记录的关注者，以及每个关注者订阅了哪些子类型。新消息的子类型在订阅列表里，关注者才会收到通知
mail.activity计划活动：给某人安排在某天对某条记录做某事
mail.activity.type活动类型：邮件、电话、会议、待办……可以自行配置
discuss.channelDiscuss 里的频道和私聊（Odoo 17 之前叫 mail.channel）

字段变更跟踪

在继承了 mail.thread 的模型上，给字段加 tracking=True，字段值改变时 chatter 里就会自动记一条「旧值 → 新值」： 

stage_id = fields.Many2one("library.checkout.stage", tracking=True)
书中的小错误

书里写的字段属性是 tracked=True，正确的写法是 tracking=True（也可以写一个整数，表示显示顺序）。

⇪ Odoo 20 变化

书里说变更日志存放在 mail.tracking.value 模型。Odoo 20 里，「旧值 → 新值」默认直接渲染进消息正文，mail 模块本身不再有这个模型； 如果需要可供查询、审计的结构化变更记录，可以安装 Discuss Tracking（mail_tracking）模块，它会重新提供 mail.tracking.value 模型和对应菜单。

多数时候，我们只需要调用几个 API（message_post()、activity_schedule() 等，见第 8 章），不用关心数据怎么存。 但当你需要精细控制「谁在什么情况下收到通知」时，理解子类型和关注者订阅的关系就很有用了。

小结

  • res.* 是业务主数据，ir.* 描述 Odoo 自身，mail.* 是消息系统。在开发者模式下的「设置 → 技术」菜单里可以查看它们。
  • res.partner 是一切「人、组织、地址」的基础；用户和公司都通过 partner_id 关联一个联系人。
  • 访问安全：用户属于 res.groups，组之间可以包含（implied_ids），Odoo 20 用 ir.access 一张表描述模型权限和记录范围。
  • 模型、字段、XML ID、菜单、视图、动作都是数据库里的记录，这就是 Odoo 可以在界面上自定义、在 XML 里声明的基础。
  • 系统参数存在 ir.config_parameter；公司相关字段在 Odoo 20 存为表内 jsonb 列，后备默认值在 ir.default。
  • 消息、关注者、活动都用「模型名 + id」软引用业务记录；字段变更跟踪用 tracking=True。

动手练习

  1. 打开开发者模式，在「技术 → 数据库结构 → 模型」里找到 library.book，查看它有哪些字段、来自哪些模块。
  2. 在「技术 → 序列与标识符 → 外部标识符」里搜索 library_app，看看第 3 章的 XML 文件创建了哪些记录。
  3. 在「技术 → 用户界面 → 视图」里找出 library.book 的表单视图，有几个继承视图？分别来自哪个模块？
  4. 在「技术 → 参数 → 系统参数」里找到 web.base.url。想一想：部署到生产环境后，为什么要确认这个值是正确的公网地址？
  5. 给借书单的 stage_id 和 member_id 字段加上 tracking=True，修改一张借书单，观察 chatter 里出现的变更记录。
