第 3 章

第一个 Odoo 应用

在 Odoo 里做开发，几乎就等于「写模块」。这一章我们从一个空目录开始，写出一个图书馆应用 library_app。 它很小，但五脏俱全：模型、权限、视图、业务逻辑、网页、自动化测试全都有。后面的每一章，都是在它的基础上继续长出新功能。

本章目标

  • 理解一个 Odoo 模块由哪些文件组成，学会写清单文件 __manifest__.py
  • 掌握「改代码 → 重启 / 升级 → 看效果」的开发循环
  • 为应用定义用户组和访问规则（Odoo 20 的 ir.access）
  • 用 Python 定义模型，用 XML 定义菜单、动作、表单、列表和搜索视图
  • 给表单加一个按钮，调用 Python 方法；再写一个简单的网页
  • 写自动化测试，并让它们通过

和 Odoo 自带的应用一样，图书馆应用有两个用户组：

第 1 步：创建模块

模块和应用

插件模块（addon module）就是一个包含 __manifest__.py 文件的目录，它可以添加新功能，也可以修改已有功能。 有些模块被标记为应用（app）：它们是某个业务领域的顶层模块，会出现在「应用」菜单里，比如 CRM、项目、人力资源。 非应用模块通常依赖某个应用，给它添加或修改功能。

判断标准很简单：带来一整块新功能的，做成应用；只是改改已有应用的，做成普通模块。图书馆是全新的功能，所以是应用。

准备插件路径

我们为图书馆项目单独建一个插件目录 ~/work20/library，项目里的所有模块都放这里。 把一个大项目拆成多个小模块是好习惯：每个模块更专注，复杂度更低。 

mkdir ~/work20/library
source ~/work20/env20/bin/activate
(env20) $ odoo scaffold library_app ~/work20/library
(env20) $ odoo --addons-path="~/work20/library,~/work20/odoo/addons" \
    -d library -c ~/work20/library.conf --save --stop
  • odoo scaffold 模块名 目录：生成一个模块骨架。先 scaffold 再保存配置，是因为 Odoo 会检查插件路径里的目录是否真的有模块，空目录会报错。
  • 第二条命令把插件路径和数据库名保存进 library.conf，以后用 -c ~/work20/library.conf 就够了。相对路径会被自动转成绝对路径保存。

启动日志的前几行有 Using configuration file at ... 和 addons paths: [...] 两行。 Odoo 找不到你的模块时，第一件事就是看这两行。

目录名就是模块的技术名，必须是合法的 Python 标识符：字母开头，只含字母、数字、下划线。 一个合法的模块目录至少要有 __manifest__.py（描述模块）和 __init__.py（让 Python 能导入它）。 __init__.py 负责导入模块里的 Python 代码，每个含 Python 文件的子目录也各有一个 __init__.py： 

from . import models
from . import controllers
⚠ scaffold 生成的权限文件是旧格式

在 Odoo 20 里，odoo scaffold 的模板仍然会生成一个 security/ir.model.access.csv， 但 ir.model.access 这个模型已经不存在了，原样安装会报错。我们会在第 5 步用新的 ir.access.csv 替换它。 scaffold 生成的其他示例文件（models.py、views.xml 等）也可以删掉，我们自己从头写。

清单文件

清单文件是一个 Python 字典。下面是图书馆应用的起点：

{
    "name": "Library Management",
    "summary": "Manage library catalog and book lending.",
    "author": "Daniel Reis",
    "license": "AGPL-3",
    "website": "https://github.com/PacktPublishing/Odoo-15-Development-Essentials",
    "version": "20.0.1.0.0",
    "category": "Services/Library",
    "depends": ["base"],
    "application": True,
}
键说明
name模块标题
summary一句话简介，显示在应用列表的标题下面
author版权作者，可以用逗号分隔多个
license许可证，常用 AGPL-3、LGPL-3；在 Odoo 商店售卖的专有模块一般用 OPL-1。不写会告警并默认为 LGPL-3
website获取更多信息的网址，比如文档或问题追踪
version模块版本。惯例是在语义化版本前加 Odoo 版本：20.0.1.0.0 表示「给 Odoo 20.0 用的 1.0.0 版」
category分类，用于在应用列表里分组，也用于组织用户组
depends依赖的模块列表。安装本模块会先安装它们
application是否作为「应用」显示在应用列表里
installable是否可安装，默认 True。设为 False 可以临时禁用模块但保留文件
auto_install设为 True 时，一旦依赖全部装好就自动安装。用于连接两个应用的「胶水模块」
⚠ 依赖一定要写全

如果你用到了某个模块的东西却没写进 depends，在你自己的库里可能碰巧能用（因为那个模块恰好已经装了、恰好先加载了）， 换一台机器、换一个干净的数据库就会安装失败或加载报错。这类问题非常难排查，宁可多写也不要漏写。

模块分类

category 可以有层级，用 / 分隔，比如项目应用属于 Services/Project。 如果写了一个不存在的分类，Odoo 会自动创建它。我们利用这一点，创建 Services/Library 分类。

分类在后面定义用户组时还要被引用，所以需要知道它的外部标识符（XML ID）。自动生成的规则是： base.module_category_ 加上分类路径（小写、空格变下划线、斜杠变下划线）。 所以 Services/Library 的 XML ID 是 base.module_category_services_library。 Odoo 自带的分类列表可以在源码 odoo/addons/base/data/ir_module_category_data.xml 里查到。

描述和图标

长描述可以写在清单的 description 键里（支持 reStructuredText 格式），也可以在模块根目录放一个 README.rst 或 README.md。 在应用商店发布的模块常用 static/description/index.html 做一个图文介绍页。 注意：application 为 True 的模块只使用 index.html，忽略 description 键。

应用需要一个图标，放在 static/description/icon.png。我们先借用一个 Odoo 自带应用的图标：

cd ~/work20/library/library_app
mkdir -p static/description
cp ~/work20/odoo/addons/maintenance/static/description/icon.png static/description/

安装模块

现在模块虽然什么功能都没有，但已经可以安装了。启动服务器时用 -i（--init）指定要安装的模块： 

(env20) $ odoo -c ~/work20/library.conf -d library -i library_app

即使配置文件里已经写了数据库，也建议在命令行再写一次 -d library，免得装错库。 安装新模块时，Odoo 会自动刷新可用模块列表，不需要先去界面上点「更新应用列表」。

开发循环：重启还是升级？

开发是一个反复迭代的过程：改代码 → 让 Odoo 用上新代码 → 看效果。关键是要知道每种修改需要做什么：

# 最常用的一条命令：重启服务器，同时升级 library_app
(env20) $ odoo -c ~/work20/library.conf -d library -u library_app

-u（--update）接受逗号分隔的模块列表，比如 -u library_app,mail。 升级一个模块时，所有依赖它的已安装模块也会跟着升级。 也可以在网页的「应用」里找到模块点「升级」，但那样不会重新加载 Python 代码。 第 2 章介绍的 --dev=all 能省掉一部分重复操作：Python 改动自动重载，视图改动直接从文件读取。

第 2 步：创建应用的骨架

一个「应用」通常应该具备三样东西：

  • 图标：static/description/icon.png，刚才已经放好了。
  • 顶级菜单：应用的所有菜单都挂在它下面。
  • 用户组：只有需要它的用户才能用，访问权限也授予这些组。

顶级菜单

菜单是用 XML 数据文件定义的。新建 views/library_menu.xml：

<odoo>
    <!-- 图书馆应用的顶级菜单 -->
    <menuitem id="menu_library"
              name="Library"
              web_icon="library_app,static/description/icon.png"/>
</odoo>

菜单、动作、视图这些界面元素，其实都是存放在数据库里的记录，Web 客户端实时读取并解释它们。 上面的文件描述的就是「要写进数据库的记录」：<menuitem> 是一种快捷写法，表示在菜单模型 ir.ui.menu 上写一条记录。

id 属性叫做 XML ID（外部标识符），用来唯一标识这条数据，让别的元素能引用它。 比如稍后添加的子菜单要指定父菜单，就写 parent="menu_library"。 web_icon 指定主菜单（应用切换器）里显示的图标，格式是「模块名,文件路径」。

Odoo 不会自动发现这个文件，必须在清单的 data 键里声明：

    "data": [
        "views/library_menu.xml",
    ],

data 是一个列表，列出模块安装或升级时要加载的数据文件，路径相对于模块根目录。 现在升级模块不会看到任何变化：菜单只有在它下面有可见的子菜单时才显示，而子菜单只有在用户有权访问对应模型时才显示。

用户组

权限是授予用户组的，用户再被分配到组里。安全相关的文件惯例放在 security/ 目录。 在 Odoo 20 里，一个应用的用户组是这样组织的：

⇪ 用户组的写法变了

书里直接给组设置 category_id（应用分类）；Odoo 19 起中间多了一层作用域（res.groups.privilege）， 组通过 privilege_id 挂到作用域上，作用域再通过 category_id 挂到分类上。 另外，组的成员字段从 users 改名为 user_ids，用户的组字段从 groups_id 改名为 group_ids。

新建 security/library_security.xml：

<odoo>
    <!-- 作用域：在用户表单的「访问权限」页里，图书馆的组会归在这一栏下 -->
    <record id="privilege_library" model="res.groups.privilege">
        <field name="name">Library</field>
        <field name="category_id" ref="base.module_category_services_library"/>
    </record>

    <!-- 图书馆用户组 -->
    <record id="library_group_user" model="res.groups">
        <field name="name">User</field>
        <field name="privilege_id" ref="privilege_library"/>
        <field name="implied_ids" eval="[Command.link(ref('base.group_user'))]"/>
    </record>

    <!-- 图书馆经理组 -->
    <record id="library_group_manager" model="res.groups">
        <field name="name">Manager</field>
        <field name="privilege_id" ref="privilege_library"/>
        <field name="implied_ids" eval="[Command.link(ref('library_group_user'))]"/>
        <field name="user_ids" eval="[Command.link(ref('base.user_root')),
                                      Command.link(ref('base.user_admin'))]"/>
    </record>
</odoo>

这里信息量不小，逐个来看：

  • <record model="..." id="...">：在指定模型上创建一条记录，并给它一个 XML ID。里面每个 <field> 是一个字段的值。
  • name：普通文本值，直接写在标签中间。
  • ref="..."：关系字段的值，通过 XML ID 引用另一条记录。
  • eval="..."：把属性值当作 Python 表达式求值。implied_ids 和 user_ids 是「对多」关系字段，要用特殊的命令语法写入。 Command.link(id) 表示「把这条记录加进去」，书里写作等价的旧式元组 (4, id)。第 5、6 章会详细讲。
  • base.user_root 是超级用户 OdooBot，base.user_admin 是默认管理员。我们把他们放进经理组，这样安装后管理员立刻就能用。

最后在清单里声明这个文件，放在菜单文件之前：

    "data": [
        "security/library_security.xml",
        "views/library_menu.xml",
    ],
★ data 列表的顺序很重要

数据文件按列表顺序依次加载，只能引用已经加载过的 XML ID。菜单和视图经常要引用用户组， 所以惯例是：安全文件在前，视图在中间，菜单在最后（菜单要引用动作，动作要先定义）。

第 3 步：先写测试

好的编程习惯包括给代码写自动化测试。对 Python 这种没有编译步骤的动态语言尤其重要：不运行，你甚至不知道有没有拼写错误。 测试驱动开发（TDD）主张先写测试、看它失败、再写功能让它通过。我们也这样做：在写模型之前，先写好测试。

Odoo 的测试基于 Python 自带的 unittest，有几条规则：

  1. 测试放在模块的 tests/ 子目录里。它不需要在模块顶层的 __init__.py 里导入，测试运行器会自己去找。
  2. 测试文件名以 test_ 开头，并在 tests/__init__.py 里导入。
  3. 测试写在继承自 Odoo 测试基类的类里，最常用的是 TransactionCase。每个以 test_ 开头的方法是一个测试用例。
  4. TransactionCase 中，每个测试用例在独立的事务里运行，结束后回滚。所以一个测试做的修改，下一个测试看不到。
from . import test_book

from odoo.tests import TransactionCase


class TestBook(TransactionCase):

    @classmethod
    def setUpClass(cls):
        super().setUpClass()
        # 用管理员身份运行测试，这样才会检查访问权限
        user_admin = cls.env.ref("base.user_admin")
        cls.env = cls.env(user=user_admin)
        cls.Book = cls.env["library.book"]
        cls.book1 = cls.Book.create({
            "name": "Odoo Development Essentials",
            "isbn": "879-1-78439-279-6",
        })

    def test_book_create(self):
        "新建的书默认是有效的"
        self.assertEqual(self.book1.active, True)

    def test_check_isbn(self):
        "检查一个合法的 ISBN"
        self.assertTrue(self.book1._check_isbn())
  • setUpClass() 在整个测试类开始前运行一次，准备测试数据。每个测试用例都能使用 cls.book1，结束后改动会被回滚。
  • 测试默认以内部的系统用户运行，它会绕过权限检查。为了顺便验证权限配置是否正确，我们用 cls.env(user=...) 把运行身份换成管理员。env.ref() 根据 XML ID 找到记录。
  • test_check_isbn 测试一个还不存在的方法 _check_isbn()，它稍后会在第 7 步实现。
⇪ 和书上代码的区别

书里在 setUp()（每个测试前都运行）里准备数据，现在更推荐用只运行一次的类方法 setUpClass()，测试更快。 另外，书中 test_check_isbn 写的是 self.assertTrue(self.book1._check_isbn)，少了一对括号 —— 它检查的是「方法对象」本身，永远为真，等于什么也没测。这里已改正。

💡 不要依赖演示数据

测试可以用演示数据省事，但那样它就只能在装了演示数据的库里跑。在测试里自己准备全部数据，测试才能在任何库（包括生产库的副本）上运行。

运行测试：升级模块时加上 --test-enable：

(env20) $ odoo -c ~/work20/library.conf -d library -u library_app --test-enable --stop

现在测试必然失败（日志里会有 ERROR），因为 library.book 模型还不存在。这正是 TDD 的第一步。

第 4 步：模型层

模型描述并存储业务对象的数据，比如一个 CRM 商机、一张销售订单、一个合作伙伴。 模型由一个继承自 Odoo 基类的 Python 类定义，ORM 负责让数据库结构和类定义保持一致，并把你的各种操作翻译成 SQL。

按照约定，模型代码放在 models/ 目录，一个模型一个文件：

from . import library_book

from odoo import fields, models


class LibraryBook(models.Model):
    _name = "library.book"
    _description = "Book"

    name = fields.Char("Title", required=True)
    isbn = fields.Char("ISBN")
    active = fields.Boolean("Active?", default=True)
    date_published = fields.Date()
    image = fields.Binary("Cover")
    publisher_id = fields.Many2one("res.partner", string="Publisher")
    author_ids = fields.Many2many("res.partner", string="Authors")
  • from odoo import fields, models：导入 Odoo 的模型和字段。
  • class LibraryBook(models.Model)：定义一个模型类。类名对 Odoo 来说无所谓，真正起作用的是 _name。
  • _name：模型的唯一标识，全系统都用它来引用这个模型。模型名用点分隔单词。
  • _description：模型的可读名称，在一些提示消息里会用到。不写会在日志里产生警告。
  • 后面七行是字段。第一个参数是字段在界面上的标签；不写的话，Odoo 会根据字段名自动生成（date_published → 「Date Published」）。
💡 命名规则一句话

模型名用点（library.book），其他一切用下划线：模块名、XML ID、数据库表名、字段名…… 多对一字段名以 _id 结尾，对多字段名以 _ids 结尾。

模型如何对应到数据库

这几个字段展示了最常用的字段类型：

  • 标量字段：Char（文本）、Boolean（布尔）、Date（日期）、Binary（二进制，这里存封面图片）。
  • publisher_id 是多对一（Many2one）关系，在数据库里就是一个外键：每本书指向一个出版社。
  • author_ids 是多对多（Many2many）关系：一本书可以有多位作者，一位作者可以写多本书。它不是表里的一列，而是 ORM 自动创建的一张中间表。
  • 出版社和作者都用了 Odoo 内置的联系人模型 res.partner —— 人、公司、地址都存在这里。
★ 两个特殊字段名
  • name：默认用作记录的显示名称 —— 别的模型引用这本书时，显示的就是它的 name。
  • active：为 False 的记录被视为「已归档」，默认在界面和搜索中自动隐藏。适合那些不再使用、但为了历史记录不能删除的数据。

升级模块后，可以在 设置 → 技术 → 数据库结构 → 模型里搜索 library.book，确认字段都建好了。还会看到几个我们没写的字段：

id
每条记录唯一的数字 ID
create_uid / create_date
创建人、创建时间
write_uid / write_date
最后修改人、最后修改时间
display_name
记录的文本表示，计算字段，默认取 name 的值

第 5 步：访问权限

模型建好了，但它还没有任何访问规则，所以谁都用不了它（包括管理员）。 这时候运行测试，test_book_create 会因为 AccessError 失败 —— 这正说明我们把测试切换到管理员身份是有意义的。 接下来把模型授权给刚才创建的两个组。

⇪ 少了一条提醒

Odoo 15 在模型缺少访问规则时，会在日志里打印 The model library.book has no access rules, consider adding one.。 Odoo 20 不再输出这条警告，所以新建模型后要记得自己补上访问规则。

用 ir.access.csv 定义访问规则

访问规则是 ir.access 模型上的记录，最方便的写法是 CSV 文件。CSV 数据文件的文件名必须等于要导入的模型名， 所以文件叫 security/ir.access.csv： 

id,name,model_id,group_id/id,operation,domain
access_book_user,Book: user,library.book,library_group_user,cru,"[('active', '=', True)]"
access_book_manager,Book: manager,library.book,library_group_manager,crud,
列含义
id这条记录的 XML ID，在本模块内唯一
name描述性名称，建议唯一，方便在界面上辨认
model_id作用于哪个模型，直接写模型名
group_id/id授予哪个组，写组的 XML ID（/id 后缀表示「按 XML ID 引用」）。留空表示这是一条对所有人生效的「限制」
operation允许的操作，由 c（创建）、r（读）、u（改）、d（删）组合而成，按 crud 的顺序书写
domain可选。只对满足这个域的记录允许上述操作；留空表示全部记录
⇪ 一个文件代替两套机制

书里用了两样东西来实现同样的效果：

  • security/ir.model.access.csv：列是 perm_read,perm_write,perm_create,perm_unlink，用 1/0 表示允许与否 —— 这是模型级权限；
  • XML 里的 ir.rule 记录，用 domain_force 限制「用户只能看有效的书」—— 这是记录级规则。

Odoo 20 把它们合并成了 ir.access，上面两行 CSV 就完整表达了书里的全部意图。 Odoo 自带的升级工具 odoo-bin upgrade_code 有一个脚本 19.4-00-ir-access.py，可以把旧的两套配置自动转换成新格式。

别忘了在清单里声明它（放在组定义之后）：

    "data": [
        "security/library_security.xml",
        "security/ir.access.csv",
        "views/library_menu.xml",

💡 也可以用 XML 写访问规则

当规则需要比较长的域，或者希望它在升级时不被覆盖（noupdate="1"，第 5 章讲）时，用 XML 写更方便：

<record id="access_book_user" model="ir.access">
    <field name="name">Book: user</field>
    <field name="model_id" ref="model_library_book"/>
    <field name="group_id" ref="library_group_user"/>
    <field name="operation">cru</field>
    <field name="domain">[('active', '=', True)]</field>
</record>

这里 model_library_book 是 ORM 为每个模型自动生成的 XML ID：model_ + 模型名（点换成下划线）。

「单据」风格的表单

对于单据类的模型，Odoo 有一种模仿纸张的表单样式：顶部 <header> 放操作按钮（和状态条），下面一张 <sheet> 放数据字段。 再用嵌套的 <group> 把字段分成左右两栏：

    <header>
        <button name="button_check_isbn" type="object" string="Check ISBN"/>
    </header>
    <sheet>
        <group name="group_top">
            <group name="group_left">
                <field name="name"/>

                <field name="publisher_id"/>
                <field name="date_published"/>
            </group>

                <field name="isbn"/>
                <field name="active"/>
                <field name="image" widget="image"/>
            </group>
        </group>

给 <group> 加 name 属性不是必须的，但强烈推荐 —— 这样别的模块在扩展这个视图时，能精确地定位到它（第 4 章）。

按钮的几个基本属性：

  • string：按钮上显示的文字。
  • type：按钮执行的动作类型。object 表示调用模型的 Python 方法；action 表示执行一个动作记录。
  • name：type="object" 时是方法名；type="action" 时是动作的 XML ID。
  • class：可选的 CSS 类，比如 oe_highlight 让按钮显示为主色调。

第 7 步：业务逻辑

现在让「Check ISBN」按钮真正工作起来。现代 ISBN 有 13 位，最后一位是根据前 12 位计算出的校验位： 前 12 位依次乘以 1、3、1、3……求和，对 10 取余；余数为 0 则校验位为 0，否则为 10 减余数。

在 models/library_book.py 的类里添加两个方法：

from odoo import fields, models
from odoo.exceptions import ValidationError


class LibraryBook(models.Model):
    _name = "library.book"
    _description = "Book"

    name = fields.Char("Title", required=True)
    isbn = fields.Char("ISBN")
    active = fields.Boolean("Active?", default=True)
    date_published = fields.Date()
    image = fields.Binary("Cover")
    publisher_id = fields.Many2one("res.partner", string="Publisher")
    author_ids = fields.Many2many("res.partner", string="Authors")

    def _check_isbn(self):
        self.ensure_one()
        digits = [int(x) for x in self.isbn if x.isdigit()]
        if len(digits) == 13:
            ponderations = [1, 3] * 6
            terms = [a * b for a, b in zip(digits[:12], ponderations)]
            remain = sum(terms) % 10
            check = 10 - remain if remain != 0 else 0
            return digits[-1] == check
        return False

    def button_check_isbn(self):
        for book in self:
            if not book.isbn:
                raise ValidationError(
                    self.env._("Please provide an ISBN for %s", book.name))
            if not book._check_isbn():
                raise ValidationError(
                    self.env._("%s ISBN is invalid", book.isbn))
        return True

理解 self：它是一个记录集

Odoo 模型方法里的 self 不是「一条记录」，而是一个记录集（recordset）：零条、一条或多条记录的集合。 所以 button_check_isbn 用 for book in self 逐条处理。表单按钮调用时 self 通常只有一条， 但用循环写，将来在列表里批量选中多本书调用也照样能用。

_check_isbn 选择了另一种风格：开头调用 self.ensure_one()，如果 self 不是恰好一条记录就立刻报错。 这适合那些「只对单条记录有意义」的辅助方法。方法名以下划线开头，表示它是私有的，不能从外部（比如按钮或 API）调用。

  • ValidationError 是 Odoo 的异常类型之一，抛出它会中止操作并把消息展示给用户，同时回滚这次请求里的数据库修改。
  • self.env._("...") 把消息标记为可翻译，参数用 %s 占位，翻译后再填入。
  • 方法最后 return True：按钮方法不需要返回值，但有些外部 API 客户端处理不了 None，所以惯例返回 True。
⇪ 翻译函数的新写法

书里的消息没有做翻译。Odoo 一直用 from odoo import _ 再 _("...") 标记可翻译文本； Odoo 18 起推荐 self.env._("...")，它直接使用当前环境的语言，参数也可以直接传进去而不是先格式化。旧写法仍然可用。

第 8 步：网页

Odoo 还自带一个 Web 开发框架，可以做出和后台数据紧密集成的网页。我们做一个最简单的页面：在 /library/books 列出书目。

生成网页的组件叫控制器（controller）：它是 http.Controller 子类里的一个方法，用 @http.route 装饰器绑定到 URL。 有人访问这个 URL 时，方法被调用，返回要显示的 HTML —— 通常用 QWeb 模板渲染。

控制器

控制器代码放在 controllers/ 目录。确认模块的 __init__.py 已经导入了 controllers，然后：

from . import main

from odoo import http
from odoo.http import request


class Books(http.Controller):

    @http.route("/library/books")
    def list(self, **kwargs):
        Book = request.env["library.book"]
        books = Book.search([])
        return request.render(
            "library_app.book_list_template",
            {"books": books},
        )
  • 类名和方法名可以随便取，起作用的是 @http.route 声明的 URL。
  • 默认 auth="user"，即必须登录才能访问；第 13 章会做公开的页面。
  • request.env 是当前请求的运行环境，用它访问模型。search([]) 用空的域查询全部（有权限看到的）书。
  • request.render() 用指定的 QWeb 模板生成 HTML，第二个参数是传给模板的变量。

这时重启服务器访问 /library/books，日志会报错 External ID not found in the system: library_app.book_list_template —— 很正常，模板还没写。

QWeb 模板

<odoo>
    <template id="book_list_template" name="Book List">
        <div id="wrap" class="container">
            <h1>Books</h1>
            <t t-foreach="books" t-as="book">
                <div class="row">
                    <span t-field="book.name"/>,
                    <span t-field="book.date_published"/>,
                    <span t-field="book.publisher_id"/>
                </div>
            </t>
        </div>
    </template>
</odoo>
  • <template> 声明一个 QWeb 模板。它其实是 ir.ui.view 记录的快捷写法，模板和后台视图存在同一个模型里。
  • t-foreach="books" t-as="book"：遍历控制器传进来的 books，每次循环把当前项叫做 book。
  • t-field="book.name"：输出记录的字段值，并按字段类型正确格式化（日期按语言习惯、多对一显示名称等）。

把它加到清单的 data 里，升级模块，登录后访问 http://localhost:8069/library/books，就能看到书目列表了。

小结

  • 模块 = 一个目录 + __manifest__.py + __init__.py。目录名就是技术名。
  • 改 Python 要重启，改模型结构和数据文件要升级（-u）；最省心的是两样一起做。
  • 数据文件必须在清单 data 里声明，按顺序加载，只能引用之前加载过的 XML ID。
  • 模型是 Python 类，_name 决定一切；ORM 把它映射成表，多对多会多一张中间表。
  • 新模型必须配访问规则才能用。Odoo 20 用一个 ir.access.csv 同时表达「哪些操作」和「哪些记录」。
  • 视图、菜单、动作、网页模板都是数据库里的记录，用 XML 数据文件定义。
  • 模型方法里的 self 是记录集；按钮用 type="object" 调用方法，抛出 ValidationError 给用户提示。
  • 控制器把 URL 绑定到 Python 方法，用 QWeb 模板生成 HTML。
