第 8 章

业务逻辑

前面几章分别学了模型（数据长什么样）和记录集（怎么操作数据）。这一章把它们组合起来，实现真正的业务流程： 会员借书，借书单从「申请」走到「已借出」再到「已归还」，过程中自动记录日期、阻止非法操作、给借书人发消息…… 同时学会写测试、打日志、调试代码 —— 这些是每天都要用的开发技能。

本章目标

  • 知道业务逻辑可以挂在哪些地方触发，以及该选哪一种
  • 掌握 ORM 方法装饰器：@api.depends、@api.constrains、@api.model、@api.model_create_multi、@api.ondelete
  • 实现「单据头 + 明细行」和「阶段 + 状态」两种常见的数据模式
  • 正确地扩展 create()、write()、unlink()
  • 用 onchange 和「可写计算字段」实现界面联动
  • 使用消息和活动；做一个向导（wizard）；抛出合适的异常
  • 写单元测试、记日志、用调试器排查问题

业务逻辑挂在哪里

业务逻辑可以由用户的动作直接触发（点按钮），也可以在某个事件发生时自动触发（写入记录）。下面是全部选项：

★ 选择的原则：越「声明式」越好

能用约束解决的，不要在 write() 里检查；能用计算字段解决的，不要在 create() 里赋值。 声明式的写法（约束、计算、默认值）让 ORM 帮你处理「什么时候执行」这个问题，扩展起来也更容易； 扩展 create() / write() 是最后的手段。

ORM 方法装饰器

方法定义前的 @... 是装饰器，它们给方法附加特定的行为：

装饰器用途
@api.depends("f1", "f2.x")计算字段的方法：声明依赖，依赖变化时重算（第 6 章）
@api.constrains("f1", ...)校验方法：这些字段被写入时执行，失败时抛异常；方法里不应该写数据（第 6 章）
@api.onchange("f1", ...)界面联动：表单上这些字段被修改时由客户端调用（本章）
@api.model方法在「模型」层面工作，self 只是模型的引用，不包含记录。默认值函数常用它
@api.model_create_multi专用于 create()：保证方法收到的总是字典列表，从而支持批量创建
@api.ondelete(at_uninstall=False)删除前的检查，抛异常可阻止删除；卸载模块时不执行
@api.private把一个公开方法标记为不能通过 RPC 调用（Odoo 18.2+）

不加装饰器的普通方法，self 是一个记录集，方法体里通常用 for 循环逐条处理。

⇪ 已经消失的装饰器

在很老的代码里你会看到 @api.multi（声明 self 是记录集，现在这是默认行为）和 @api.one（自动替你循环）。它们在 Odoo 14 被移除，遇到直接删掉。 另外，方法名以下划线开头本身就意味着「不能从外部调用」；@api.private 是给那些名字不以下划线开头、但同样不该被外部调用的方法用的。

常用的数据模式

单据头与明细行

业务单据常常是「一个头 + 若干行」：销售订单有多行商品，发票有多行明细。在 Odoo 里实现很简单：明细模型用多对一字段指向头，头模型用一对多字段列出明细。 借书单也是这样：一张借书单可以借多本书。 

from odoo import fields, models


class LibraryCheckoutLine(models.Model):
    _name = "library.checkout.line"
    _description = "Checkout Request Line"

    checkout_id = fields.Many2one("library.checkout", required=True, ondelete="cascade")
    book_id = fields.Many2one("library.book", required=True)
    note = fields.Char("Notes")

    line_ids = fields.One2many(
        "library.checkout.line",
        "checkout_id",
        string="Borrowed Books",
    )

明细行的 checkout_id 加了 ondelete="cascade"：删除借书单时，它的明细行跟着删除。 在表单里，用一个页签（notebook / page）放明细行，并在 <field> 内部嵌套一个可编辑的列表视图： 

<notebook>
    <page name="lines" string="Borrowed Books">
        <field name="line_ids">
            <list editable="bottom">
                <field name="book_id"/>
                <field name="note"/>
            </list>
        </field>
    </page>
</notebook>

一对多字段在表单里显示为一个嵌套的列表。默认情况下 Odoo 会去找明细模型的列表视图，找不到就自动生成；也可以像上面这样在字段内部直接声明要用的视图。 editable="bottom" 让用户直接在列表里编辑，新行加在底部。

阶段与状态

销售订单、项目任务、招聘申请……这些「单据」都有生命周期。表示生命周期的步骤有两种做法：

状态（state）：固定的选择列表
可选值在代码里写死，比如 草稿 / 已确认 / 已完成。
✔ 业务逻辑可以放心地判断 if state == "done"
✘ 用户无法增加自己的步骤
阶段（stage）：一个可配置的模型
阶段是另一个模型的记录，通常叫 stage_id，用户可以增删、排序、改名。
✔ 灵活，适配每家企业自己的流程
✘ 代码没法依赖某个具体阶段（ID 和名字都可能变）

两全其美的做法是：用阶段，但每个阶段映射到一个固定的状态。用户随便配置阶段，业务逻辑只看状态。借书模块就采用这种方式：

给借书单加上阶段

还要处理好两点用户体验：新单据的默认阶段应该是第一个 new 状态的阶段；按阶段分组时，没有单据的阶段也要显示出来（否则看板会缺列）。

from odoo import api, fields, models


class LibraryCheckout(models.Model):
    _name = "library.checkout"
    # ...

    @api.model
    def _default_stage_id(self):
        Stage = self.env["library.checkout.stage"]
        return Stage.search([("state", "=", "new")], limit=1)

    @api.model
    def _group_expand_stage_id(self, stages, domain):
        return stages.search([])

    stage_id = fields.Many2one(
        "library.checkout.stage",
        default=_default_stage_id,
        group_expand="_group_expand_stage_id",
    )
    state = fields.Selection(related="stage_id.state")
  • _default_stage_id 找第一个状态为 new 的阶段。阶段模型按 sequence 排序，所以拿到的是序号最小的那个。
  • group_expand 改变了按这个字段分组的行为。默认只显示「有记录的组」，指定了它之后，分组结果由这个方法决定 —— 这里返回所有有效的阶段。 它的值必须是方法名字符串（不像 default 那样可以直接引用函数）。
  • state 是一个关联字段，把阶段的状态「搬」到借书单上，方便在视图和代码里使用。
⇪ group_expand 方法少了一个参数

书里的签名是 _group_expand_stage_id(self, stages, domain, order)。Odoo 17 起去掉了 order 参数，变成 (self, stages, domain)。按老签名写会在分组时报参数错误。

给界面用的 ORM 方法

下面这些方法主要由 Web 客户端调用，也是常见的扩展点：

方法作用
_compute_display_name()计算记录的显示名称（取代了旧的 name_get()，第 6 章）
name_search(name, domain, operator, limit)在关系字段里打字时，按显示名称搜索候选记录。通常设置 _rec_names_search 就够，不必重写
name_create(name)只给一个名字就创建记录，用于关系字段里的「创建 xxx」和看板的快速创建

get_views(views)返回要渲染的视图结构（取代了旧的 fields_view_get()）

扩展 create、write 和 unlink

有些业务逻辑没法用声明式的方式表达，必须挂在记录的写操作上。ORM 的三个写方法：

  • Model.create(vals_list)：创建记录，返回新记录。参数是字典或字典列表。
  • recordset.write(vals)：用字典里的值更新记录集。
  • recordset.unlink()：删除记录。

扩展 create()

需求：不允许直接以「已借出」或「已归还」的状态创建借书单。这个检查和「创建」这个事件强相关，用普通约束不好表达，所以扩展 create()： 

from odoo import api, exceptions, fields, models

    # （在 LibraryCheckout 类中）
    @api.model_create_multi
    def create(self, vals_list):
        # super() 之前：只能使用 vals_list 里的值
        new_records = super().create(vals_list)
        # super() 之后：可以使用新建的记录
        for checkout in new_records:
            if checkout.stage_id.state in ("open", "done"):
                raise exceptions.UserError(
                    self.env._("State not allowed for new checkouts."))
        return new_records

新记录由 super().create() 创建。在它之前，新记录还不存在，只能读取（甚至修改）vals_list； 在它之后，可以通过 checkout.stage_id.state 这样的点号链访问新记录的数据。状态是固定的、可以被代码信赖，所以检查状态而不是阶段。 抛出异常会让整个创建操作回滚。

⇪ create 必须是「批量」的

书里写的是 @api.model def create(self, vals)，一次只处理一个字典。Odoo 12 起 create() 就支持批量， 现在的规范写法是 @api.model_create_multi + vals_list（无论调用方传入单个字典还是列表，方法里拿到的都是列表）， 旧的单字典写法会在日志里产生废弃警告，并且会让批量创建退化成逐条创建。书中检查的状态值 "close" 也是个笔误，应为 "done"。

扩展 write()

需求：记录借出日期和归还日期。这不能用计算字段做（它们是「某个时刻」的快照，不是能从当前数据推算出来的值），所以扩展 write()，在阶段变化时设置日期： 

    checkout_date = fields.Date(readonly=True)
    close_date = fields.Date(readonly=True)

    def write(self, vals):
        # super() 之前：self 里还是旧值，通过修改 vals 来补充要写入的内容
        if "stage_id" in vals:
            Stage = self.env["library.checkout.stage"]
            new_state = Stage.browse(vals["stage_id"]).state
            if new_state == "open":
                vals["checkout_date"] = fields.Date.today()
            elif new_state == "done":
                vals["close_date"] = fields.Date.today()
        return super().write(vals)

这里在 super() 之前检查 vals，就能知道「即将发生什么变化」。注意 vals["stage_id"] 是一个数字 ID， 需要 browse() 成记录才能读它的状态。只要可能，就像这样修改 vals 而不是直接给字段赋值 —— 原因见下一节。

在 write() 里给字段赋值：小心无限递归

有时候必须在 super() 之后再写数据（比如需要对比每条记录写入前后的状态）。但在 write() 里给本记录赋值，会再次调用 write()， 进而再次赋值……直到 Python 抛出递归错误。解决办法是在上下文里放一个标记： 

    def write(self, vals):
        old_states = {checkout.id: checkout.state for checkout in self}
        result = super().write(vals)
        # super() 之后：self 已经是新值
        if not self.env.context.get("_checkout_write"):
            for checkout in self:
                old_state, new_state = old_states[checkout.id], checkout.state
                if new_state != old_state and new_state == "open":
                    checkout.with_context(_checkout_write=True).write(
                        {"checkout_date": fields.Date.today()})
                if new_state != old_state and new_state == "done":
                    checkout.with_context(_checkout_write=True).write(
                        {"close_date": fields.Date.today()})
        return result

删除前检查：@api.ondelete

如果要阻止某些记录被删除（比如还有书没还的借书单），不要重写 unlink()，而是用 @api.ondelete 装饰一个检查方法： 

    @api.ondelete(at_uninstall=False)
    def _unlink_except_borrowed(self):
        if any(checkout.state == "open" for checkout in self):
            raise exceptions.UserError(
                self.env._("You can't delete a checkout whose books are still borrowed."))

at_uninstall=False 的意思是：卸载模块时不执行这个检查。否则这种检查会让模块无法卸载（卸载需要删除模块的全部数据）。 这正是推荐它而不是重写 unlink() 的原因。

什么时候（不）该扩展 create 和 write

需求更好的做法
某个字段的值可以根据其他字段算出来（比如单据总额）计算字段
默认值不是固定的默认值函数
改了 A 字段，B 字段跟着变（但 B 允许手动修改）可写计算字段（下一节）
校验数据@api.constrains
阻止删除@api.ondelete
以上都不行，比如默认值依赖同一条新记录的其他字段这时才扩展 create() / write()

导入导出的 ORM 方法

第 5 章的导入导出功能，在 ORM 里对应两个方法：

  • load(fields, data)：导入。fields 对应 CSV 的表头，data 是行的列表，每行是字符串值的列表。支持 XML ID 等全部导入特性。
  • export_data(fields)：导出。字段名可以带 /id、.id 后缀，返回格式与可导入的 CSV 兼容。

界面联动：onchange 与可写计算字段

用户在表单上编辑时，常常希望「改了这个，那个自动跟着变」。Odoo 有两种实现方式。

经典 onchange

    @api.onchange("member_id")
    def onchange_member_id(self):
        today_date = fields.Date.today()
        if self.request_date != today_date:
            self.request_date = today_date
            return {
                "warning": {
                    "title": "Changed Request Date",
                    "message": "Request date changed to today!",
                }
            }
  • @api.onchange 列出「触发字段」（不支持点号路径）。表单上这些字段一变，客户端就调用这个方法。
  • 方法里的 self 是一条虚拟记录，包含表单当前的全部值（可能还没保存过）。给它赋值，不会写数据库，只会更新表单上显示的值。
  • 可以返回一个带 warning 键的字典，在界面上弹出提示（不阻止操作）。
⇪ onchange 不能再返回 domain

书里提到 onchange 还可以返回 {"domain": {"user_id": [...]}} 动态修改其他字段的可选范围。这个能力在 Odoo 17 被移除。 现在的做法是在视图里给字段写一个依赖其他字段的动态域，比如 <field name="book_id" domain="[('publisher_id', '=', publisher_id)]"/>， 或者用一个计算字段算出允许的记录，再在域里引用它。

经典 onchange 的局限

  • 只在表单里生效。它由客户端触发，通过代码或 API 直接 write() 时根本不会执行，服务端逻辑得自己再调用一遍。
  • 挂在「触发字段」上，而不是「被影响的字段」上。逻辑一复杂，很难看出某个字段到底会被哪些 onchange 改动，也不好扩展。

可写计算字段：新式的 onchange

Odoo 13 起，计算字段的能力被扩展来覆盖这个场景：给字段加上计算方法，同时 store=True 和 readonly=False。 依赖的字段变化时自动重算 —— 无论是在表单里还是通过代码写入；而用户也可以手动覆盖算出来的值。 

    request_date = fields.Date(
        default=lambda s: fields.Date.today(),
        compute="_compute_request_date",
        store=True,
        readonly=False,
    )

    @api.depends("member_id")
    def _compute_request_date(self):
        for checkout in self:
            checkout.request_date = fields.Date.today()

和普通计算方法相比，可写计算字段的方法可以只在满足条件时赋值（比如某个值为空时才填默认值），没赋值的记录保留原值。 但它不能弹提示：计算方法的返回值会被忽略。如果确实需要提示用户，那就还得用经典 onchange。

⚠ 书中示例的问题

书里把 onchange 方法几乎原样改成了计算方法，包括 return {"warning": ...} 和直接使用 self.request_date（没有循环）。 这两点在计算方法里都不对：返回值不起作用；self 可能包含多条记录，必须循环处理。上面的写法已修正。

消息、关注者、子类型

消息可以带一个子类型，用来区分事件、精细控制通知。子类型在 设置 → 技术 → 讨论 → 子类型里配置，基本的有：

子类型XML ID用途
Discussionsmail.mt_comment「发送消息」：关注者会收到通知
Notemail.mt_note「记录备注」：只记录，不通知
Activitiesmail.mt_activities计划活动产生的消息，不用于通知

应用还可以定义自己的子类型，比如销售应用有「报价单已发送」「销售订单已确认」。在关注者菜单里，可以为每个关注者单独勾选他要接收哪些子类型的通知。

发消息

# 记录一条备注（默认 mail.mt_note，不发通知）
checkout.message_post(body="Hello!")

# 发一条消息，通知所有关注者
checkout.message_post(
    body="Hello again!",
    subject="Hello",
    subtype_xmlid="mail.mt_comment",
)

# 消息正文是 HTML。普通字符串会被转义；要发 HTML，用 Markup 包装
from markupsafe import Markup
checkout.message_post(body=Markup("<b>请尽快归还</b>"))
⇪ message_post 的参数变了
  • Odoo 20 的 message_post() 只接受关键字参数，书里的 self.message_post("Hello!") 要写成 message_post(body="Hello!")。
  • 指定子类型用 subtype_xmlid="mail.mt_comment"，书里的 subtype= 参数已不存在。
  • 为了防止 XSS，普通字符串正文会被当作纯文本转义；需要 HTML 时用 markupsafe.Markup（Html 字段读出来的值本身就是 Markup）。

添加关注者

checkout.message_subscribe(partner_ids=checkout.member_id.partner_id.ids)   # 关注者是联系人
checkout.message_subscribe(partner_ids=some_users.partner_id.ids)           # 要加用户，就加他的联系人

新关注者会使用默认的子类型；也可以传入 subtype_ids=[...] 指定（会重置该关注者已有的订阅）。

向导

向导（wizard）是一种交互模式：弹出一个对话框，让用户填一些信息，然后执行某个自动化操作。 我们做一个「群发消息」向导：图书管理员在借书单列表里选中若干单据（比如逾期未还的），从「操作」菜单打开向导，填写标题和正文，点「发送」，就给每张借书单发一条消息、通知借书人。

向导模型

向导和普通功能一样用「模型 + 视图」实现，只是模型继承自 models.TransientModel。它的数据也存在数据库里，但只是临时的，定时任务会定期清掉。 

from . import checkout_mass_message

import logging

from odoo import api, exceptions, fields, models
from odoo.fields import Command

_logger = logging.getLogger(__name__)


class CheckoutMassMessage(models.TransientModel):
    _name = "library.checkout.massmessage"
    _description = "Send Message to Borrowers"

    checkout_ids = fields.Many2many("library.checkout", string="Checkouts")
    message_subject = fields.Char()
    message_body = fields.Html()

    @api.model
    def default_get(self, field_names):
        defaults_dict = super().default_get(field_names)
        if "checkout_ids" in field_names and self.env.context.get("active_model") == "library.checkout":
            checkout_ids = self.env.context.get("active_ids", [])
            defaults_dict["checkout_ids"] = [Command.set(checkout_ids)]
        return defaults_dict

    def button_send(self):
        self.ensure_one()
        if not self.checkout_ids:
            raise exceptions.UserError(self.env._("No Checkouts were selected."))
        if not self.message_body:
            raise exceptions.UserError(self.env._("A message body is required."))
        for checkout in self.checkout_ids:
            checkout.message_post(
                body=self.message_body,
                subject=self.message_subject,
                subtype_xmlid="mail.mt_comment",
            )
            _logger.debug(
                "Message on %d to followers: %s",
                checkout.id,
                checkout.message_follower_ids,
            )
        _logger.info(
            "Posted %d messages to the Checkouts: %s",
            len(self.checkout_ids),
            self.checkout_ids.ids,
        )
        return True
⚠ 临时模型和普通模型之间别用一对多

普通模型不应该有指向临时模型的关系字段。如果向导上有一个一对多字段指向普通模型，普通模型就得有一个指回向导的多对一字段 —— 向导记录被自动清理时就会出问题。 所以向导里关联普通记录用多对多：关系表里的行会随任意一边的删除而自动删除。

预填数据：default_get()

向导表单刚打开时，只是一个空表单，向导记录还没有被创建（create() 要等到用户点按钮时才执行）。所以预填数据只能靠「默认值」。 default_get() 是 ORM 计算默认值的方法，扩展它就能加上自己的默认值。

那怎么知道用户在列表里选中了哪些记录？第 7 章讲过：从一个视图跳到另一个视图时，Web 客户端会把来源信息放进上下文 —— active_model（来源模型）、active_id（当前记录）、active_ids（选中的记录列表）。 我们从 active_ids 拿到 ID，用 Command.set() 设给多对多字段。先检查 active_model 是一个好习惯，防止向导从别的地方被打开时用错 ID。

向导的按钮逻辑

点击按钮时，self 就是刚刚根据表单数据创建出来的向导记录。方法只处理一条向导记录，用 ensure_one() 明确这一点。 方法遍历选中的借书单，给每一张发一条 mail.mt_comment 子类型的消息，这样关注者会收到邮件通知。 方法最后返回 True：有些 XML-RPC 客户端处理不了 Python 的 None，养成总是返回点什么的习惯。

向导的访问规则

临时模型和普通模型一样需要访问规则（Odoo 13 起）。推荐只给创建、读、改，不给删除。到这里，借书模块完整的访问规则文件是：

抛出异常

当输入不合适、操作不该被执行时，代码要中断执行并告诉用户原因 —— 这就是抛出异常。Odoo 在 odoo.exceptions 里提供了专用的异常类：

异常什么时候用
UserError操作违反了业务规则，告诉用户哪里不对。最常用
ValidationError数据校验失败，用在 @api.constrains 方法里
AccessError没有权限。ORM 会自动抛出，你一般不需要自己抛
MissingError记录不存在（比如已被别人删除）
RedirectWarning出错的同时给用户一个按钮，跳转到能解决问题的地方（比如「去配置」）

一次方法调用里所有的数据修改都在同一个数据库事务里，一旦抛出异常，之前所做的全部修改都会被撤销。 所以检查放在前面还是后面都不会留下半截数据，但尽早检查可以少做无用功。前面向导里的两个检查就是例子。

单元测试

自动化测试是公认的最佳实践。它不仅确认代码按预期工作，更重要的是为将来的修改和重构提供了一张安全网。 对 Python 这种没有编译步骤的语言，测试还能抓出拼写错误之类的低级问题。写测试有两个目标：覆盖率（每一行代码都至少被一个测试执行过）和正确性。

测试类

测试放在 tests/ 子目录，不需要在模块的 __init__.py 里导入；tests/__init__.py 导入各个测试文件：

from . import test_checkout_mass_message

Odoo 提供的主要测试基类：

  • TransactionCase：每个测试方法在自己的保存点里运行，结束后回滚；测试之间互不影响。setUpClass() 里准备的数据对所有测试可见，最后统一回滚。
  • HttpCase：在 TransactionCase 基础上能发起 HTTP 请求、驱动无头浏览器，用于测试网页和前端交互（「tour」测试）。
⇪ SingleTransactionCase 已被移除

书里的测试用的是 SingleTransactionCase（所有测试共用一个事务、按名字顺序执行、相互依赖）。它在 Odoo 20 中已经不存在了。 改用 TransactionCase，并把共享的测试数据放在 setUpClass() 里 —— 既有接近的速度，又保持测试之间相互独立。 另外，Odoo 20 中模块测试默认带 post_install 标签：在所有模块安装完之后才运行。

编写测试

from odoo import exceptions
from odoo.tests import TransactionCase


class TestWizard(TransactionCase):

    @classmethod
    def setUpClass(cls):
        super().setUpClass()
        # 以管理员身份运行，顺便检查访问规则
        admin_user = cls.env.ref("base.user_admin")
        cls.env = cls.env(user=admin_user)
        cls.Checkout = cls.env["library.checkout"]
        cls.Wizard = cls.env["library.checkout.massmessage"]
        a_member = cls.env["library.member"].create(
            {"partner_id": admin_user.partner_id.id})
        cls.checkout0 = cls.Checkout.create({"member_id": a_member.id})

    def test_01_button_send(self):
        """Send 按钮应在借书单上生成一条消息"""
        count_before = len(self.checkout0.message_ids)
        Wizard0 = self.Wizard.with_context(
            active_model="library.checkout",
            active_ids=self.checkout0.ids,
        )
        wizard0 = Wizard0.create({
            "message_subject": "Hello",
            "message_body": "This is a message.",
        })
        wizard0.button_send()
        count_after = len(self.checkout0.message_ids)
        self.assertEqual(
            count_before + 1,
            count_after,
            "Expected one additional message in the Checkout.",
        )

    def test_02_button_send_empty_body(self):
        """正文为空时 Send 按钮应报错"""
        Wizard0 = self.Wizard.with_context(
            active_model="library.checkout",
            active_ids=self.checkout0.ids,
        )
        wizard0 = Wizard0.create({})
        with self.assertRaises(exceptions.UserError):
            wizard0.button_send()
  • 测试方法名以 test_ 开头才会被发现；方法的 docstring 会在运行时打印到日志，用来描述这个测试在测什么。
  • 发消息的方法没有返回值可以检查，所以换个思路：数一数执行前后借书单上的消息数，应该多一条。 assertEqual 的最后一个参数是测试失败时显示的说明，强烈建议写上。其他断言方法见 unittest 文档。
  • 运行向导需要模拟界面的流程：用 with_context() 放入 active_ids，create() 出向导记录（相当于用户填好表单），再调用按钮方法。
  • 测试「应该抛异常」的情况，把代码放进 with self.assertRaises(异常类): 块里：没有抛出这个异常，测试就失败。
💡 用 Form 模拟真实表单

odoo.tests.Form 能像用户一样操作一个表单：设置字段会触发 onchange 和计算字段，保存时走正常的创建流程。测试界面联动逻辑时特别有用：

    f.member_id = a_member          # 会触发 request_date 的重算
checkout = f.record                 # 退出 with 时自动保存

日志

写日志对监控和审计运行中的系统很有用，也方便日后排查问题而不必改代码。在文件顶部准备一个日志对象：

import logging

_logger = logging.getLogger(__name__)

_logger.debug("一条 DEBUG 消息")
_logger.info("一条 INFO 消息")
_logger.warning("一条 WARNING 消息")
_logger.error("一条 ERROR 消息")

__name__ 是当前 Python 模块的名字（如 odoo.addons.library_checkout.wizard.checkout_mass_message），这样日志会标明消息来自哪个文件。 向导里的 _logger.info(...) 会在日志里输出： 

INFO library odoo.addons.library_checkout.wizard.checkout_mass_message: Posted 2 messages to the Checkouts: [3, 4]
★ 不要自己格式化日志字符串

写 _logger.info("Hello %s", name)，不要写 _logger.info("Hello %s" % name) 或 f-string。 把参数交给日志模块，它只在这条消息真的要输出时才格式化，被过滤掉的 debug 消息就不会白白消耗时间。

debug 级别的消息默认不输出（默认级别是 INFO）。用第 2 章讲过的选项打开：--log-level=debug 打开全部； 更精确地只打开某个文件的： 

odoo -c library.conf --log-handler=odoo.addons.library_checkout.wizard.checkout_mass_message:DEBUG

调试

服务器开发选项

回顾第 2 章：开发时用 --dev=all 启动，Python 代码保存后自动重载（需要 pip install watchdog），视图直接从 XML 文件读取。改了模型结构仍然需要升级模块。

Python 调试器

Odoo 是一个服务器：等待请求、执行 Python 代码、返回结果。所以断点是设在服务器端的，程序在断点处暂停时，要在运行服务器的那个终端里操作调试器。 设置断点只需在代码里加一行： 

    def button_send(self):
        breakpoint()          # Python 3.7+ 内置；等价于 import pdb; pdb.set_trace()
        self.ensure_one()
        # ...

重启服务器，打开向导点「发送」，浏览器会一直转圈，而服务器终端里出现调试提示符：

> /home/you/work20/library/library_checkout/wizard/checkout_mass_message.py(35)button_send()
-> self.ensure_one()
(Pdb) self.checkout_ids
library.checkout(1,)
(Pdb) n

第一行是文件、行号和函数名，第二行是下一行要执行的代码。最常用的命令：

命令作用命令作用
h帮助l列出当前位置附近的代码
p 表达式打印表达式的值pp 表达式美化打印（字典、列表）
n执行到下一行（不进入函数）s进入当前行调用的函数
c继续运行到下一个断点q退出（中断执行）
u / d在调用栈里上移 / 下移bt显示完整调用栈

调试提示符里可以执行任意 Python 表达式，甚至修改变量。直接回车会重复上一条命令。

💡 调试时的小麻烦
  • 调试期间日志会不断插进来。用 --log-handler=odoo.http.server:WARNING 关掉请求日志，或 --log-level=warn 降低整体日志级别。
  • 退出调试器后终端如果「失灵」（输入不显示），盲打 reset 回车即可恢复。
  • 更好用的调试器：pip install ipdb（带补全和高亮）或 pudb（全屏的终端界面）。设置环境变量 PYTHONBREAKPOINT=ipdb.set_trace 后，breakpoint() 就会使用它。
  • VS Code、PyCharm 等编辑器也可以直接附加到 Odoo 进程做图形化调试：用编辑器的 Python 调试配置运行 odoo-bin 即可。
⇪ --dev 不再自动进入调试器

书里的 --dev=all 会在出现未处理异常时自动进入 pdb，并支持 --dev=ipdb 等选项。Odoo 20 的 --dev 不再包含这些功能，需要断点时用 breakpoint()。

print 与日志

有时只想看看某个变量的值，或确认某段代码有没有执行到，print() 就够了，它不会暂停程序。但打印内容只输出到标准输出，日志写文件时不会记录。 print 只能作为开发时的辅助手段，不要带进正式代码；如果它对排查生产环境的问题也有帮助，就改成 debug 级别的日志。

检查运行中的进程

先找到 Odoo 进程的 PID（每条日志时间戳后面的数字就是，也可以用 ps ax | grep odoo），然后可以给它发信号：

kill -3 <PID>       # SIGQUIT：在日志里打印所有线程当前的调用栈（不会停止服务）
kill -HUP <PID>     # 重启服务器（重新加载代码和配置）
kill -TERM <PID>    # 正常关闭

kill -3 在服务器「卡住」时特别有用：它告诉你每个线程此刻正在执行哪一行代码。 更系统的性能分析可以用 Odoo 自带的性能分析器：开发者模式下的调试菜单里可以开启 profiling，结果在 设置 → 技术 → 数据库结构 → Profiling 里查看。

小结

  • 业务逻辑可以挂在字段定义（约束、计算、默认值）、记录事件（create / write / ondelete / onchange）、用户动作（按钮、服务器动作、向导）以及定时任务和自动化规则上。优先选择声明式的方式。
  • 「单据头 + 明细行」用一对多 + 多对一实现；「阶段 + 状态」兼顾了可配置性和代码的可靠性；group_expand 让空阶段也显示出来。
  • 扩展 create() 用 @api.model_create_multi；扩展 write() 优先修改 vals，需要在 super 之后写入时用上下文标记防递归；阻止删除用 @api.ondelete。
  • 界面联动：经典 @api.onchange 只在表单里生效、可以弹提示；可写计算字段在任何写入时都生效，是更推荐的方式。
  • mail.thread / mail.activity.mixin 提供消息、关注者和活动；message_post(body=..., subtype_xmlid=...) 发消息。
  • 向导 = 临时模型 + 表单视图 + 带 binding_model_id 和 target="new" 的窗口动作；用 default_get 读取 active_ids 预填数据。
  • UserError 告诉用户操作不合法，异常会回滚整个事务。
  • 测试用 TransactionCase + setUpClass；日志用 logging 并把参数交给日志模块格式化；调试用 breakpoint()。
