第 1 章

用开发者模式快速上手

在装开发环境、写 Python 之前，先在浏览器里把一个小应用「点」出来。 这一章不写任何代码，但你会亲手碰到 Odoo 应用的每一个零件：模型、字段、视图、菜单、动作和访问权限。 后面的章节只是把这些零件改成用代码来写。

本章目标

  • 知道 Odoo 是什么、社区版和企业版的区别、版本是怎么发布的
  • 理解 Odoo 的三层架构：数据层、逻辑层、表现层
  • 打开开发者模式，学会用它查看任何界面背后的技术信息
  • 只用界面操作，做出一个「待办事项」应用：新模型、新字段、菜单、视图、权限
⇪ 关于版本

原书基于 Odoo 15（2021 年发布）。本教程全部改用 Odoo 20（2026 年 9 月发布）讲解。 界面和代码里凡是和书上不一样的地方，都会用这种紫色提示框标出来，附录（第 16 章）还有一张完整的对照表。

要做的东西：一个待办应用

这一章的例子很简单：一个待办事项（To-do）清单。需求如下：

  • 可以新建待办事项，比如「买鸡蛋」，完成后勾上「已完成？」。
  • 每个待办只有创建它的人能看到 —— 别人的待办你看不见。
  • 一个待办可以指定若干位协作者，称为「工作组」（Work Team）。协作者从联系人里选，但只有被标记为「工作组成员」的联系人才能被选中。

先认识 Odoo

Odoo 和它的社区

Odoo 是比利时公司 Odoo S.A. 开发的开源业务软件，创始人是 Fabien Pinckaers。 它最早叫 TinyERP，后来改名 OpenERP，2014 年起叫 Odoo。它既是一整套现成的业务应用（CRM、销售、库存、会计、网站……）， 也是一个开发业务应用的框架。本教程关心的是后者。

Odoo 采用「开放核心」模式，发布两个版本：

  • 社区版（CE）：完全开源，本教程用的就是它。
  • 企业版（EE）：在 CE 之上加一层专有模块，提供额外功能，需要订阅。
  • OCA（Odoo 社区协会）：一个非营利组织，托管了几百个仓库的高质量社区模块，并制定了统一的编码规范。遇到通用需求，先去 github.com/OCA 搜一下，很可能已经有人做好了。

版本节奏

Odoo 每年秋天在 Odoo Experience 大会上发布一个大版本，官方同时支持最近的三个大版本。 两个大版本之间，Odoo Online（官方 SaaS）还会滚动发布 x.1、x.2… 这样的中间版本， 新特性通常先在中间版本里出现，再汇入下一个大版本。

⚠ 大版本之间互不兼容

Odoo 的数据库和模块都绑定大版本：Odoo 20 的服务器打不开 Odoo 19 建的数据库， 为 Odoo 15 写的模块也不能直接装进 Odoo 20。从网上下载社区模块时，一定要确认它对应的版本分支（比如 20.0）。 这也是为什么书里的代码需要改写之后才能在 Odoo 20 上运行。

同一个大版本内部（例如 20.0 的各次小更新）只修 bug，保证 API 稳定：模型结构和视图元素的标识不会变， 你的自定义模块不会因为升级小版本而坏掉。而 master 分支是下一个大版本的开发中代码，随时在变，不要拿来做项目。

Odoo 的架构

理解 Odoo 应用由哪几层组成，对后面学习每一种组件都有帮助：

数据层
Odoo 只支持 PostgreSQL 一种数据库，这是有意的设计。附件、图片等二进制文件默认存在磁盘上一个叫 filestore 的目录里。 所以完整备份一个 Odoo 实例 = 数据库转储 + filestore 的拷贝，缺一不可。
ORM
对象关系映射（Object-Relational Mapping）。你几乎不用写 SQL：在 Python 里定义一个模型类，ORM 就帮你建表； 调用 create()、search()、write()、unlink() 就完成增、查、改、删。 ORM 同时负责权限检查和数据一致性，所以原则上只应该通过它访问数据库。
逻辑层
在 ORM 之上扩展的业务规则，比如在 create() 里自动设置默认值、写一个校验方法、自动计算某个字段。
表现层
Odoo 自带一个功能齐全的 Web 客户端（就是你登录后看到的后台），它通过 RPC 调用服务器。另有一个网站框架， 用控制器和 QWeb 模板生成面向公众的网页。服务器 API 是公开的，官方 Web 客户端用的 API，别的程序也能用。

用 Docker 跑一个 Odoo 20

需要两个容器：一个 PostgreSQL，一个 Odoo。Odoo 20 要求 PostgreSQL 16 或更高：

# 1. 启动数据库容器
docker run -d --name db \
  -e POSTGRES_USER=odoo -e POSTGRES_PASSWORD=odoo -e POSTGRES_DB=postgres \
  postgres:17

# 2. 启动 Odoo 容器，连到上面的数据库，把 8069 端口映射出来
docker run -t -p 8069:8069 --name odoo --link db:db odoo:20.0

看到服务器日志滚动之后，浏览器打开 http://localhost:8069，按提示创建一个数据库即可。 镜像标签以 Docker Hub 上的 odoo 官方镜像为准。几个常用命令：

命令作用
docker stop odoo停止容器
docker start -a odoo启动容器，并把日志输出到当前终端
docker ps列出正在运行的容器
docker rm -f odoo db删掉两个容器，从头再来
💡 端口被占用？

如果 8069 已经被别的 Odoo 占了（比如 Windows 安装器装的服务），把 -p 8069:8069 改成 -p 8070:8069，然后访问 8070 端口。

打开开发者模式

开发者模式（也叫调试模式，debug mode）会在界面上暴露 Odoo 的内部配置： 每个字段的技术名、每个视图的 XML、菜单背后的动作……并允许你直接修改。它是本章的主要工具， 也是以后你写代码时查看「这个界面是怎么做出来的」最快的办法。

打开方式有两种：

  1. 进入 设置（Settings）应用，拉到页面底部的 开发者工具（Developer Tools）区域，点 Activate the developer mode。
  2. 或者直接改地址栏：在网址后加上 ?debug=1。例如 http://localhost:8069/odoo?debug=1。
⇪ 网址变了

Odoo 15 的后台地址是 /web#...，书里让你改成 /web?debug=1#...。 从 Odoo 18 起后台改成了更易读的 /odoo/... 形式（如 /odoo/contacts/7）， 所以现在写成 /odoo?debug=1。旧的 /web 地址仍然会自动跳转过去。

打开之后界面上会多出这些东西：

  • 顶部导航栏右侧出现一个小虫子图标，就是调试菜单。它的内容随当前页面变化。
  • 设置应用顶部出现技术（Technical）菜单 —— 所有底层配置的入口。
  • 鼠标悬停在任意字段标签上，会弹出这个字段的技术信息：字段名、类型、关联模型、所用的组件（widget）等。

还有一个变体叫 Activate the developer mode (with assets)（网址里是 ?debug=assets）。 平时浏览器加载的 JavaScript 和 CSS 是压缩合并过的，这个模式改为加载未压缩的单个文件，方便调试前端代码，代价是页面变慢。 只有调试 Web 客户端本身时才需要它。

⚠ 能力越大，责任越大

开发者模式下的修改是直接作用在数据库上的。请在测试库里练习，不要在生产系统上随手改。 另外，这种「在界面上改」的方式很难纳入版本控制、自动测试和「测试环境 → 生产环境」的发布流程 —— 这正是我们后面要学用代码写模块的原因。本章把它当作理解 Odoo 内部结构的窗口和快速做原型的工具。

ⓘ 关于 Odoo Studio

企业版和在线版有一个叫 Studio 的可视化应用构建器，能用拖拽完成本章的大部分操作。 社区版没有它，所以我们用开发者模式和「技术」菜单 —— 它们在所有版本里都有，只是更「技术」一些。

给已有模型加一个字段

第一个需求：在联系人上加一个「是工作组成员？」的勾选框。联系人是 Odoo 核心自带的模型（技术名 res.partner）， 如果主菜单里还没有「联系人」应用，先去 应用（Apps）里搜索 Contacts 并安装。

第一步：在模型上加字段

  1. 打开 联系人应用，点调试菜单（小虫子）→ Fields。你会看到联系人模型现有的全部字段。
  2. 点 新建（New），填写：
    • Field Name（字段名）：x_is_work_team
    • Field Label（标签）：Is Work Team?
    • Field Type（类型）：boolean（布尔，即勾选框）
  3. 保存。
★ 为什么一定要 x_ 开头

在界面上创建的模型和字段，技术名必须以 x_ 开头。这样它们就和模块代码定义的东西永远不会重名， Odoo 也能一眼认出哪些是「手工定制」。用代码写的模块没有这个限制。

第二步：把字段放到表单上

字段已经存在于模型（也就是数据库表）里了，但界面上还看不到它 —— 模型和视图是分开的。 我们要把它放进联系人的表单视图，比如放在「标签（Tags）」字段后面。

  1. 打开任意一个联系人的表单，把鼠标悬停在「标签」上，看到它的技术名是 category_id。这就是我们的「插入点」。
  2. 调试菜单 → View: Form，打开当前表单视图的定义。
  3. 不要直接改 Architecture 里的 XML！切到 Inherited Views（继承视图）标签页，添加一行，新建一个扩展视图：
    • View Name：Contacts Form extensions for To-do App
    • Architecture：填入下面这段 XML
  4. 保存，刷新页面，「Is Work Team?」就出现在标签下面了。
<field name="category_id" position="after">
    <field name="x_is_work_team"/>
</field>

这段 XML 的意思是：「找到名为 category_id 的字段，在它之后插入 x_is_work_team 字段。」

★ 为什么不直接改原视图

原视图属于某个模块（这里是 base）。模块一升级，它的视图就会被模块文件里的版本覆盖，你直接改的内容会全部丢失。 扩展视图是独立的记录，升级不会碰它。「不改原件，叠加修改」是 Odoo 定制的核心思想，第 4 章会用代码系统地讲。

视图类型

刚才改的是表单视图。Odoo 的界面由多种视图组成，最常见的几种：

视图XML 根元素用途
列表（List）<list>以表格形式浏览多条记录
表单（Form）<form>查看、编辑单条记录的全部细节
看板（Kanban）<kanban>以卡片展示记录，可按列分组（比如 CRM 的销售管道）。联系人应用默认就是看板
搜索（Search）<search>不直接显示数据，而是控制搜索框、筛选（Filters）和分组（Group By）的选项

其他视图（日历、透视表、图表、活动……）在第 10 章介绍。

⇪ tree 改名为 list

书里的列表视图根元素是 <tree>，视图类型也叫 Tree。从 Odoo 18 开始统一改名为 <list>， 动作里的 view_mode 也从 tree,form 变成了 list,form。本教程一律使用新名字。

所有视图定义都可以在 设置 → 技术 → 用户界面 → 视图里看到。更方便的办法是去 设置 → 技术 → 数据库结构 → 模型，找到 res.partner，打开它的「视图」标签页，这里只列这个模型的视图。

一个模型的同一种视图可以有多个基础视图（「继承自」字段为空的就是基础视图）。比如联系人就有 base.view_partner_form 和 base.view_partner_simple_form 两个表单。没有特别指定时， Odoo 使用序号（Sequence）最小的那个；窗口动作也可以指定使用哪一个。

创建一个新模型

模型是应用的骨架：它定义了数据结构，ORM 会为它在数据库里建一张表。我们的「待办事项」模型需要三个字段：描述、是否完成、工作组。

模型名用单数（「待办事项」而不是「待办事项们」）。技术名只能用字母和下划线，又因为是在界面上建的，必须加 x_ 前缀， 所以叫 x_todo_item。

  1. 打开 设置 → 技术 → 数据库结构 → 模型，点 新建。
  2. Model Description（模型描述）填 To-do Item，Model（技术名）填 x_todo_item。
  3. 字段列表里已经有一个 x_name 字段 —— 它是记录的「标题」，在列表和别处引用这条记录时显示。正好用作待办的描述，把它的标签改成 Description 之类即可。
  4. 添加一行，新建字段：Field Name x_is_done，Label Is Done?，Type boolean。
  5. 再添加一行，新建「工作组」字段：
    • Field Name：x_work_team_ids
    • Field Label：Work Team
    • Field Type：many2many
    • Related Model（关联模型）：res.partner
    • Domain（域）：[('x_is_work_team', '=', True)]
  6. 保存模型。

多对多关系

「工作组」比前两个字段复杂：它指向另一个模型的记录，而且可以选多个。 一个待办可以有多位协作者，一位联系人也可以参与多个待办 —— 这就是多对多（many2many）关系。

域（Domain）：Odoo 的筛选条件语法

Domain 属性是可选的，用来限制「可以选哪些记录」。这里我们只允许选勾了「工作组成员」的联系人。 域表达式是 Odoo 特有的语法：一个由三元组组成的列表，每个三元组是一个条件。

💡 不会写域？让 Odoo 帮你生成

在列表视图的搜索框里用「筛选 → 添加自定义筛选」，Odoo 会弹出一个可视化的条件编辑器，开发者模式下还会同时显示对应的域代码。 照着它抄，是学习域语法最快的方式。

保存模型后，打开它会发现字段列表里多了几个你没建的字段：id、create_uid（创建人）、create_date（创建时间）、 write_uid（最后修改人）、write_date（最后修改时间）。ORM 给每个模型都自动加上它们，用于审计追踪。 待会儿做「每人只看自己的待办」时就要用到 create_uid。

菜单和窗口动作

模型有了，但用户还没有入口。我们要创建一个顶级菜单「To-do」，点击后直接打开待办列表。

  1. 打开 设置 → 技术 → 用户界面 → 菜单项，点新建：Menu 填 To-do，Parent Menu（上级菜单）留空。
  2. Action（动作）一栏，类型选 ir.actions.act_window，在旁边的输入框里输入 To-do Items，下拉中选「创建并编辑…」。
  3. 在弹出的动作表单里，Action Name 填 To-do Items，Model（目标模型）填 x_todo_item。保存动作，再保存菜单。

刷新浏览器……菜单并没有出现。为什么？因为当前用户还没有被授权访问这个模型。权限在下一节解决，我们先把菜单和动作的关系搞清楚。

动作有好几种类型，最重要的三种：

  • 窗口动作（ir.actions.act_window）：打开视图展示数据，最常用。
  • 报表动作（ir.actions.report）：生成报表，第 12 章。
  • 服务器动作（ir.actions.server）：在服务器上执行一段自动化逻辑。
💡 快捷方式

在任何页面打开调试菜单 → Action，就能直接编辑「打开当前页面的那个窗口动作」，不用去技术菜单里找。

访问权限

Odoo 内置了严格的访问控制：用户只能用被授权的功能。新建的模型默认谁都不能访问 —— 包括管理员。 （Odoo 12 之前管理员可以绕过权限，现在不行了。）

访问控制建立在两个概念上：

用户组（Group）
一组用户的集合。权限是授予「组」的，用户属于哪些组，就拥有哪些权限。组可以隐含（imply）其他组： 成为 A 组成员，就自动成为它所隐含的 B 组成员，权限叠加。一般每个应用至少提供「用户」和「管理员」两个组。
访问规则（Access）
Odoo 20 用一个统一的模型 ir.access 描述「谁、对哪个模型、能做哪些操作（增/查/改/删）、限于哪些记录（域）」。
⇪ 权限系统在 Odoo 20 里重做了

书里（以及 Odoo 19 以前）有两套东西：访问控制列表（ir.model.access，管模型级别的增删改查）和 记录规则（ir.rule，用域限制能访问哪些记录），要分开配置。 Odoo 20 把两者合并成了一个模型 ir.access：一条访问规则同时包含「操作」和「域」两部分。 界面上原来的 Record Rules 菜单也不见了，统一在 设置 → 技术 → 安全 → Access Rights。 另外，用户组表单里原来的「应用」字段，现在叫作用域（Scope），对应 res.groups.privilege。

第一步：创建用户组

进入 设置 → 用户与公司 → 组（这个菜单需要开发者模式），新建：

  • Name：To-Do User
  • 在 Dependencies（依赖）标签页加一行，选择 Role / User（即内部用户组，技术标识 base.group_user）

这样，「To-Do User」组就隐含了内部用户组：加入 To-Do User 的人自动拥有内部用户的全部权限（比如读取联系人）， 所以我们不需要再单独给联系人模型授权。应用的用户组通常都会这样继承内部用户组。

第二步：创建访问规则

需求是「每个人只能看到并操作自己创建的待办」。在 Odoo 20 里，一条访问规则就能表达：

  1. 打开 设置 → 技术 → 安全 → Access Rights，点新建。
  2. 名称：To-do User: own items。
  3. Model：To-do Item；Group：To-Do User。
  4. Operations 标签页：勾上 Create、Read、Update、Delete 四项。
  5. Domain：[('create_uid', '=', user.id)]，保存。

域里的 user 是一个特殊变量，代表当前登录的用户记录，可以用点号访问它的属性，比如 user.id。 create_uid 是 ORM 自动维护的「创建人」字段。所以这个域的意思就是「创建人是我」。

「许可」与「限制」

Odoo 20 的访问规则分成两类，判断依据只有一个：有没有填 Group。

许可（Permission）：填了 Group
给这个组的成员授予某些操作，域限定作用于哪些记录。
一个用户命中多条许可时，它们之间是「或」：任意一条允许就可以。
限制（Restriction）：Group 留空
对所有人生效、无法绕过的全局限制，最典型的是多公司隔离。
多条限制之间是「且」：必须全部满足。

第三步：把自己加进组

  1. 进入 设置 → 用户与公司 → 用户，打开 Mitchell Admin（默认管理员）。
  2. 在 访问权限（Access Rights）标签页找到 To-Do User，勾上并保存。
  3. 刷新浏览器。To-do 菜单出现了！

点进去，你会发现即使我们还没建任何视图，Odoo 也能显示列表和表单 —— 框架会为没有视图的模型自动生成简单的默认视图。 用管理员和 Demo 用户各建几条待办试试：每个人只能看到自己的。

超级用户

Odoo 内部还有一个超级用户，叫 OdooBot，数据库 ID 为 1。它绕过所有权限检查， 供系统内部操作使用。它没有登录密码，但管理员可以从调试菜单选择 Become Superuser 临时切换成它； 在登录页（/web/login?debug=1）下方也有 Log in as superuser。 进入超级用户模式后，右上角会显示黄黑相间的警示条纹。

⚠ 能不用就不用

超级用户无视一切权限，在多公司等场景下很容易造出不一致的数据。只有在确实需要时才用，用完立即退出。

创建视图

自动生成的视图太简陋了。我们来写自己的列表视图、表单视图和搜索视图。它们都在 设置 → 技术 → 用户界面 → 视图里新建。

列表视图

新建视图：View Name To-do List View，View Type List，Model x_todo_item，Architecture 填：

<list>
    <field name="x_name"/>
    <field name="x_is_done"/>
</list>

结构很简单：一个 <list> 元素，里面每个 <field> 是一列。

表单视图

再新建一个：View Name To-do Form View，View Type Form，Model x_todo_item：

<form>
    <group>
        <field name="x_name"/>
        <field name="x_is_done"/>
        <field name="x_work_team_ids"
               widget="many2many_tags"
               context="{'default_x_is_work_team': True}"/>
    </group>
</form>

这里有两个值得注意的属性：

  • widget="many2many_tags"：多对多字段默认显示成一个子列表，换成这个组件后显示为一排「标签」，更紧凑。
  • context="{'default_x_is_work_team': True}"：关系字段允许用户直接在下拉框里新建一个联系人。 既然只有工作组成员才能被选，那新建的联系人就该默认勾上这个标记。default_字段名 这种上下文键就是用来设置默认值的。
ⓘ 不填 View Type 也行

Odoo 会根据 Architecture 的根元素自动识别视图类型。

搜索视图

列表上方的搜索框，以及它下面的「筛选」「分组」选项，都由搜索视图控制。我们加一个「未完成」筛选： 

<search>
    <filter name="item_not_done"
            string="Not Done"
            domain="[('x_is_done', '=', False)]"/>
</search>

保存后刷新待办列表，「筛选」下拉里就有 Not Done 了。注意这里又用到了域：一个筛选就是一个带名字的域。

默认开启筛选

如果希望一打开列表就只看未完成的，但用户仍可以手动取消，可以在窗口动作的上下文里设置默认筛选：

  1. 打开待办列表，调试菜单 → Action。
  2. 在 Context Value（上下文）里填：{'search_default_item_not_done': True}，保存。

search_default_ 前缀告诉搜索视图「默认选中名为 item_not_done 的筛选」。 前面表单里的 default_ 前缀设置字段默认值，这里的 search_default_ 设置默认筛选 —— 上下文（context）是 Odoo 里到处都在用的「传递额外信息」的机制，以后会反复见到。

小结

  • Odoo 是开源的业务应用平台，也是开发框架。社区版是地基，企业版和社区模块都是叠在上面的模块。
  • 大版本每年一个、互不兼容；本教程用 Odoo 20，书中的 Odoo 15 写法会在紫色框里标注差异。
  • 三层架构：PostgreSQL + filestore 存数据，Python 服务器通过 ORM 承载业务逻辑，Web 客户端 / 网站 / 外部程序负责表现。
  • 开发者模式（?debug=1）暴露字段技术名、视图 XML、动作和权限，是你最常用的侦查工具。
  • 一个最小的应用 = 模型（数据）+ 访问规则（谁能用）+ 菜单和动作（入口）+ 视图（界面）。
  • 不要修改别人的视图，用扩展视图叠加修改。
  • Odoo 20 用 ir.access 统一了访问控制：有组的是「许可」（彼此为或），没组的是「限制」（彼此为且）。

动手练习

  1. 给待办模型再加一个「截止日期」字段（类型 date），把它加到列表和表单视图里。
  2. 在搜索视图里加一个按「是否完成」分组的选项。提示：<filter name="group_done" string="完成状态" context="{'group_by': 'x_is_done'}"/>。
  3. 用 Demo 用户登录，确认他看不到 To-do 菜单；把他加进 To-Do User 组后再试。
  4. 打开 设置 → 技术 → 安全 → Access Rights，搜索模型 res.partner，看看 Odoo 自带了哪些关于联系人的访问规则，哪些是「许可」，哪些是「限制」。
  5. 用调试菜单查看「销售」或「CRM」应用里任意一个表单的视图 XML，试着找出其中你在本章见过的元素。
