第 15 章

部署与维护

应用开发完了，最后一公里是把它部署到服务器上给真正的用户使用。生产环境和开发环境的要求很不一样： 它要开机自动运行、要扛住多人同时使用、要通过 HTTPS 加密、要能安全地升级和回滚。 这一章我们在一台全新的 Ubuntu 服务器上，一步步搭出一个「小规模生产可用」的 Odoo 20。

先说清楚

服务器的搭建和运维本身是一门专业。本章介绍的是 Odoo 部署中最重要的配置和最佳实践，足以让你理解每一块在做什么、搭出一个合理安全的服务器； 但对于存放敏感数据的关键系统，仍然建议请有经验的系统管理员把关（防火墙、备份策略、监控、数据库调优等本章不展开）。

本章目标

  • 准备 Ubuntu 24.04 主机：系统依赖、PostgreSQL、专用系统用户
  • 从源码安装 Odoo 20，并编写生产用的配置文件
  • 理解多进程 worker 模式，以及如何估算 worker 数量
  • 把 Odoo 配置成 systemd 服务，开机自启
  • 用 Nginx 做反向代理，启用 HTTPS 和 WebSocket
  • 建立预发布（staging）环境，安全地更新代码和升级模块

准备主机

Odoo 通常部署在 Debian 系的 Linux 上，Ubuntu 是云服务器上最常见的选择。本章以 Ubuntu 24.04 LTS 为例。 它自带的 Python 3.12 和 PostgreSQL 16 正好满足 Odoo 20 的最低要求。

⇪ Odoo 20 的版本要求

Odoo 20 需要 Python 3.12 – 3.14 和 PostgreSQL 16 或更高版本。书中使用的 Ubuntu 20.04 自带 Python 3.8、PostgreSQL 12，都已经不够用了。

安装系统依赖

先更新软件包，然后安装 PostgreSQL：

sudo apt update
sudo apt upgrade -y
sudo apt install -y postgresql
数据库也可以在另一台服务器上

Odoo 可以连接一台独立的 PostgreSQL 服务器。那样的话这台机器就不用装 PostgreSQL，只要在配置文件里填上 db_host、db_port、db_user、db_password。

接着是编译 Python 依赖所需的系统包。和第 2 章开发环境用的一样： 

sudo apt install -y git python3-dev python3-pip python3-venv \
    build-essential libpq-dev libxml2-dev libxslt1-dev \
    libldap2-dev libsasl2-dev libssl-dev libjpeg-dev zlib1g-dev
另一种方式：用 Debian 软件包

Odoo 源码里的 setup/debinstall.sh 脚本会读取 debian/control 文件，用 apt 安装 Odoo 需要的全部系统包（包括 Python 库的 Debian 版本）。 克隆源码后运行 sudo ./setup/debinstall.sh 即可；加 --list 参数只列出包名不安装。

最后是生成 PDF 报表用的 wkhtmltopdf（第 12 章讲过，这里再重复一次）：

wget https://github.com/wkhtmltopdf/packaging/releases/download/0.12.6.1-3/wkhtmltox_0.12.6.1-3.jammy_amd64.deb \
     -O /tmp/wkhtml.deb
sudo apt install -y /tmp/wkhtml.deb
wkhtmltopdf --version     # 应显示 0.12.6.1 (with patched qt)

创建专用的系统用户

良好的安全习惯是用一个没有任何特权的专用用户来运行 Odoo。万一 Odoo 被攻破，攻击者也只能拿到这个用户的权限： 

sudo adduser --system --home=/opt/odoo --group odoo

--system 创建一个系统用户（不能登录、没有密码），--home=/opt/odoo 把它的主目录设为 /opt/odoo， 我们会把 Odoo 的代码放在这里。--group 同时创建同名的用户组。

然后给它创建一个同名的 PostgreSQL 账号：

sudo -u postgres createuser --createdb odoo

这个数据库账号不是超级用户，只有「创建数据库」的权限：它可以创建并拥有自己的数据库，但碰不到 PostgreSQL 里的其他东西。 PostgreSQL 在本机默认使用「peer」认证：Linux 用户 odoo 连接时自动对应数据库用户 odoo，不需要密码。

更严格的做法

Odoo 日常运行其实不需要「数据库所有者」权限，只有安装、升级模块时才需要。安全要求更高的场合，可以让 Odoo 服务用一个非所有者的数据库账号运行， 维护操作再用所有者账号单独执行。Odoo 不允许用 postgres 超级用户运行，会直接报错退出。

从源码安装 Odoo 20

Odoo 也提供 Debian/Ubuntu 的安装包，但从源码安装更灵活：可以精确控制部署的版本，打补丁、回滚都方便，还能和 Git 工作流结合。 以下操作都以 odoo 用户的身份执行： 

sudo -u odoo -H bash          # 切换为 odoo 用户（它不能直接登录）
cd /opt/odoo
git clone https://github.com/odoo/odoo.git odoo20 -b 20.0 --depth=1
git clone https://github.com/你的账号/library.git library     # 你自己的模块仓库

-b 20.0 选择 20.0 分支；--depth=1 只下载最新的一次提交，不要几十万条历史记录，下载更快、占用更小。 自定义模块一般也用 Git 管理，同样克隆到服务器上。

然后在虚拟环境里安装 Python 依赖和 Odoo 本身：

python3 -m venv /opt/odoo/env20
source /opt/odoo/env20/bin/activate
(env20) $ pip install -U pip
(env20) $ pip install -r /opt/odoo/odoo20/requirements.txt
(env20) $ pip install -e /opt/odoo/odoo20
(env20) $ odoo --version
Odoo Server 20.0
(env20) $ exit                  # 回到你自己的用户

下面几种启动方式效果相同，在脚本里常用最后一种，因为它不需要先激活虚拟环境：

命令说明
odoo --version激活虚拟环境后，使用 pip install -e 生成的 odoo 命令
/opt/odoo/odoo20/odoo-bin --version直接运行源码里的启动脚本（同样需要激活虚拟环境）
/opt/odoo/env20/bin/python /opt/odoo/odoo20/odoo-bin --version用虚拟环境里的 Python 运行启动脚本
/opt/odoo/env20/bin/odoo --version直接调用虚拟环境里的 odoo 命令，最简洁

配置 Odoo

生成并放置配置文件

Linux 上配置文件习惯放在 /etc 下，所以我们使用 /etc/odoo/odoo.conf。先让 Odoo 生成一份包含全部默认选项的文件，方便以后查看有哪些选项： 

sudo -u odoo /opt/odoo/env20/bin/odoo -c /opt/odoo/odoo.conf --save --stop-after-init \
    --db-filter='^odoo-prod$' --proxy-mode --no-database-list \
    --addons-path=/opt/odoo/odoo20/addons,/opt/odoo/library

sudo mkdir /etc/odoo
sudo cp /opt/odoo/odoo.conf /etc/odoo/odoo.conf
sudo chown root:odoo /etc/odoo/odoo.conf
sudo chmod 640 /etc/odoo/odoo.conf     # root 可写，odoo 组只读，其他人不可见

sudo mkdir /var/log/odoo
sudo chown odoo:odoo /var/log/odoo

-c 指定配置文件路径；--save 把命令行上的选项写进文件（文件不存在就创建，内容是全部默认值加上你给的选项）； --stop-after-init 让它做完就退出。把文件交给 root 所有、odoo 组只读，Odoo 进程能读但不能改，配置里的密码也不会被其他用户看到。

重要的配置项

用编辑器打开 sudo nano /etc/odoo/odoo.conf，确认下面这些关键选项：

[options]
addons_path = /opt/odoo/odoo20/addons,/opt/odoo/library
admin_passwd = 一个很长的随机密码
db_name = odoo-prod
dbfilter = ^odoo-prod$
list_db = False
http_interface = 127.0.0.1
http_port = 8069
gevent_port = 8072
proxy_mode = True
workers = 6
max_cron_threads = 1
limit_time_cpu = 600
limit_time_real = 1200
logfile = /var/log/odoo/odoo-server.log
data_dir = /opt/odoo/.local/share/Odoo
选项作用
addons_path逗号分隔的模块目录列表，从左到右查找，左边的优先。Odoo 内核自带的 odoo/addons 会自动加入，不必写
admin_passwd「主密码」，用于网页上的数据库管理功能（建库、删库、备份）。一定要改成强密码；Odoo 启动后会把它自动替换为哈希值
db_name默认使用的数据库
dbfilter正则表达式，限定这个服务能访问哪些数据库。写成 ^库名$，用户就不会被要求选择数据库，公开网页（如第 13 章的书目页）也能正常工作。支持 %h（请求的主机名）和 %d（子域名）占位符，可以实现「一个域名一个库」
list_db设为 False 会隐藏数据库列表，并关闭网页上的数据库管理器及其接口
http_interface监听的地址。默认 0.0.0.0（所有网卡）；Nginx 和 Odoo 在同一台机器时设为 127.0.0.1，外界就无法绕过 Nginx 直接访问 Odoo
http_port / gevent_port普通 HTTP 请求的端口（默认 8069）和 WebSocket 长连接的端口（默认 8072）
proxy_mode在反向代理后面运行时必须设为 True，Odoo 才会信任代理传来的 X-Forwarded-* 请求头（见后面 Nginx 一节）
workers大于 0 时启用多进程模式，见下一节
limit_time_cpu / limit_time_real单个请求允许消耗的 CPU 时间 / 实际时间（秒），超过就终止该 worker。默认 60 / 120，导入大文件、生成大报表时可能不够
logfile日志文件位置。不设置时日志输出到标准输出（systemd 会收进 journal）
data_dir存放附件（filestore）和会话的目录。备份时它和数据库同样重要
两个必须设置的安全选项

admin_passwd（强密码）和 list_db = False 在任何连上互联网的 Odoo 服务器上都必须设置，否则任何人都可能通过网页上的数据库管理器下载、甚至删除你的数据库。 生成随机密码可以用 openssl rand -base64 32。

⇪ Odoo 20 变化

书中的 without_demo = all 不再需要：从 Odoo 18.3 起，新数据库默认不加载演示数据，想要演示数据反而要显式加 --with-demo。 书中 Nginx 配置里的长轮询端口 longpolling_port 也已改名为 gevent_port（实时通信从「长轮询」改为了 WebSocket）。

初始化数据库并试运行

用 Odoo 20 的 odoo db 命令创建并初始化生产数据库，同时设置管理员密码、语言和公司所在国家： 

sudo -u odoo /opt/odoo/env20/bin/odoo db -c /etc/odoo/odoo.conf \
    init odoo-prod --language zh_CN --country CN \
    --username admin --password '另一个强密码'

然后手动启动一次，在另一个终端里观察日志，确认没有报错：

sudo -u odoo /opt/odoo/env20/bin/odoo -c /etc/odoo/odoo.conf
# 另开一个终端：
tail -f /var/log/odoo/odoo-server.log

因为日志写进了文件，第一个终端里不会有任何输出，这是正常的。确认无误后按 Ctrl+C 停止。

在一个终端里开多个窗口

用 tmux 或 GNU screen 这样的终端复用工具，可以在一个 SSH 连接里同时开多个窗口，即使网络断开，里面的程序也会继续运行。

理解多进程 worker

默认情况下 Odoo 以单进程、多线程的方式运行。由于 Python 的全局解释器锁（GIL），这样只能利用一个 CPU 核心。 设置 workers = N（N ≥ 1）后，Odoo 切换到多进程（prefork）模式：

  • 经验公式：workers = 2 × CPU 核数 + 1。如果 PostgreSQL 也在同一台机器上，要适当减少。
  • 宁多勿少：浏览器会对同一个网站并发发起多个请求，所以至少设为 6 比较合适。上限主要由内存决定，每个 worker 都会占用一部分内存。
  • 容量估算：一般使用模式下，一个 worker 大约能服务 6 个同时在线的用户。
  • 自动回收：limit_memory_soft、limit_memory_hard、limit_request、limit_time_* 这些限制达到时，主进程会结束该 worker 并启动一个新的，防止内存泄漏或个别请求拖垮整个服务器。
  • 生成 PDF 至少需要 2 个 worker：wkhtmltopdf 渲染时会回头向 Odoo 请求样式和图片（第 12 章）。
内存怎么算？

默认 limit_memory_soft 是 2 GB、limit_memory_hard 是 2.5 GB，这是单个 worker 的上限，而不是平均占用。 一般的 worker 平时只用几百 MB。规划内存时可以粗略按「worker 数 × 平均占用 + PostgreSQL + 系统」估算，再留出余量。

配置成系统服务

生产环境里的 Odoo 应该作为系统服务运行：开机自动启动，不依赖任何人登录。现在的 Ubuntu 用 systemd 管理服务， 只需要写一个描述文件 /etc/systemd/system/odoo.service： 

[Unit]
Description=Odoo 20
After=network.target postgresql.service

[Service]
Type=simple
User=odoo
Group=odoo
ExecStart=/opt/odoo/env20/bin/odoo -c /etc/odoo/odoo.conf
KillMode=mixed
Restart=on-failure

[Install]
WantedBy=multi-user.target

它基于 Odoo 源码里的 debian/odoo.service 示例，改了 ExecStart 的路径，并加上 Restart=on-failure（进程意外退出时自动重启）。 日志位置已经在配置文件的 logfile 里设置了，所以这里不用重复。 

sudo systemctl daemon-reload          # 让 systemd 读取新的服务文件
sudo systemctl enable --now odoo      # 设为开机自启，并立即启动
sudo systemctl status odoo            # 查看状态
sudo systemctl restart odoo           # 重启（更新代码后用）
sudo systemctl stop odoo              # 停止
书中的小差异

书中的服务文件放在 /lib/systemd/system/，那里是软件包安装服务文件的位置，系统管理员自己写的应该放在 /etc/systemd/system/； 书中 ExecStart 写的是 /opt/odoo/env/bin/odoo，而前文创建的虚拟环境叫 env15，路径要和实际一致； 参数 --logfile 写成了 --log-file（仓库里的脚本）也是错的。

在命令行检查服务

在服务器上用 curl 确认 Odoo 在响应：

$ curl -I http://localhost:8069
HTTP/1.1 303 SEE OTHER
Location: http://localhost:8069/odoo
...
$ curl -s http://localhost:8069/web/version
{"version_info": [20, 0, 0, "final", 0, ""], "version": "20.0"}

根路径会把你重定向到后台 /odoo；/web/version 返回版本号，很适合做健康检查。查看日志： 

less /var/log/odoo/odoo-server.log       # 翻看
tail -f /var/log/odoo/odoo-server.log    # 实时跟踪
sudo journalctl -u odoo -e               # systemd 记录的启动 / 崩溃信息
日志轮转

日志文件会一直变大。可以参照 Odoo 源码里的 debian/logrotate，在 /etc/logrotate.d/odoo 里配置按周轮转、压缩旧日志。

Nginx 反向代理

Odoo 自己就能提供网页服务，但生产环境中强烈建议在它前面放一个反向代理。反向代理接收所有客户端的请求，再转交给后面的 Odoo：

🔒

安全

处理并强制 HTTPS 加密；隐藏内部网络结构；还可以充当应用防火墙，只放行允许的 URL。

⚡

性能

缓存静态文件、压缩响应，减轻 Odoo 的负担；必要时把请求分发到多台 Odoo 服务器（负载均衡）。

先安装 Nginx，删掉默认站点，建立 Odoo 站点的配置文件：

sudo apt install -y nginx
sudo rm /etc/nginx/sites-enabled/default
sudo nano /etc/nginx/sites-available/odoo
sudo ln -s /etc/nginx/sites-available/odoo /etc/nginx/sites-enabled/odoo

Nginx 的约定是：配置写在 sites-available 里，在 sites-enabled 里建一个指向它的符号链接才算启用。 先写一个只用 HTTP 的基本配置，确认代理工作正常： 

upstream odoo {
    server 127.0.0.1:8069;
}
upstream odoochat {
    server 127.0.0.1:8072;
}
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

server {
    listen 80;
    server_name odoo.mycompany.com;

    proxy_read_timeout 720s;
    proxy_connect_timeout 720s;
    proxy_send_timeout 720s;

    access_log /var/log/nginx/odoo.access.log;
    error_log  /var/log/nginx/odoo.error.log;

    # WebSocket：实时通知、聊天
    location /websocket {
        proxy_pass http://odoochat;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 其他所有请求
    location / {
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_redirect off;
        proxy_pass http://odoo;
    }

    gzip on;
    gzip_types text/css text/plain text/xml application/xml application/json application/javascript;
}
  • upstream 定义后端服务的地址：8069 处理网页和 RPC 请求，8072 处理 WebSocket 长连接（即时消息、通知等实时功能）。
  • /websocket 需要额外的 Upgrade / Connection 请求头，把 HTTP 连接「升级」为 WebSocket；上面的 map 就是为此准备的。
  • X-Forwarded-* 请求头告诉 Odoo 原始请求的主机名、协议和客户端 IP。
  • gzip 压缩文本类响应，加快页面加载。
为什么 proxy_mode 必须和请求头一起用

经过 Nginx 之后，所有到达 Odoo 的请求都来自 127.0.0.1。打开 proxy_mode 后，Odoo 会从 X-Forwarded-For 取出真实的客户端 IP、 从 X-Forwarded-Proto 得知用户用的是 HTTPS（这样生成的链接、跳转才正确）。 但如果开了 proxy_mode 却没有让代理强制设置这些请求头，恶意客户端就可以自己伪造它们。 另外，Odoo 只在请求带有 X-Forwarded-Host 时才启用代理处理，所以这个头不能漏。

⇪ Odoo 20 变化

书中把 /longpolling 路径转发给 8072 端口。从 Odoo 16 起，实时通信改用 WebSocket，路径是 /websocket， 而且必须转发 Upgrade / Connection 请求头；照搬书中配置的话，聊天和通知将无法实时更新。

检查配置语法，然后让 Nginx 重新加载（reload 不会中断正在进行的连接）：

$ sudo nginx -t
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
$ sudo systemctl reload nginx

配置并强制 HTTPS

网络流量不应该以明文在互联网上传输，尤其是登录密码。Odoo 对外提供服务时，必须使用 HTTPS。

获取证书

推荐使用 Let's Encrypt 的免费证书，它被所有浏览器信任，certbot 工具会自动申请证书、修改 Nginx 配置并定期续期： 

sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d odoo.mycompany.com

前提是域名已经解析到这台服务器、80 端口可以从外网访问。如果只是内网测试，没有公网域名，也可以生成一个自签名证书： 

sudo mkdir -p /etc/ssl/nginx
sudo openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
    -keyout /etc/ssl/nginx/server.key -out /etc/ssl/nginx/server.crt
sudo chmod 600 /etc/ssl/nginx/server.key
自签名证书的局限

自签名证书能加密流量，但浏览器无法验证它，会显示安全警告，也无法防止中间人攻击。只适合测试。对外提供服务、尤其是有网上商城时，一定要用受信任机构签发的证书。

HTTPS 版的 Nginx 配置

把前面的 server 块拆成两个：80 端口只负责把请求重定向到 HTTPS，443 端口才真正提供服务： 

# upstream 和 map 与前面相同，省略

# http -> https
server {
    listen 80;
    server_name odoo.mycompany.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name odoo.mycompany.com;

    ssl_certificate     /etc/ssl/nginx/server.crt;
    ssl_certificate_key /etc/ssl/nginx/server.key;
    ssl_session_timeout 30m;
    ssl_protocols TLSv1.2 TLSv1.3;

    proxy_read_timeout 720s;
    proxy_connect_timeout 720s;
    proxy_send_timeout 720s;

    access_log /var/log/nginx/odoo.access.log;
    error_log  /var/log/nginx/odoo.error.log;

    location /websocket {
        proxy_pass http://odoochat;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
        add_header Strict-Transport-Security "max-age=31536000; includeSubDomains";
        proxy_cookie_flags session_id samesite=lax secure;
    }

    location / {
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
        add_header Strict-Transport-Security "max-age=31536000; includeSubDomains";
        proxy_cookie_flags session_id samesite=lax secure;
        proxy_redirect off;
        proxy_pass http://odoo;
    }

    # 缓存静态文件（各模块的 /模块名/static/...）
    location ~* ^/[^/]+/static/ {
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_pass http://odoo;
        expires 7d;
    }

    gzip on;
    gzip_types text/css text/plain text/xml application/xml application/json application/javascript;
}
  • return 301 https://...：把所有 http:// 访问永久重定向到对应的 https:// 地址，防止有人不小心用明文访问。
  • Strict-Transport-Security（HSTS）：告诉浏览器「以后一年内都只用 HTTPS 访问这个域名」。
  • proxy_cookie_flags ... secure：给会话 Cookie 加上 Secure 标志，它只会通过 HTTPS 发送。
  • 静态文件：Odoo 的静态文件路径都是 /模块名/static/...。expires 7d 让浏览器缓存它们 7 天，下次打开页面不用再请求。资源包的 URL 里带有内容哈希，更新后 URL 会变，不用担心缓存过期的问题。
书中配置的过时之处

书中的 ssl on; 指令在 Nginx 1.15 已弃用、1.25 起移除，现在要写成 listen 443 ssl;；书中只允许 TLSv1.2，建议加上 TLSv1.3。 另外书中的静态缓存只匹配 /web/static/，其他模块（包括我们自己的）的静态文件不会被缓存；而单独写 proxy_cache_valid 却没有用 proxy_cache 定义缓存区，这行其实不会生效。

重新加载并测试：

sudo nginx -t &amp;&amp; sudo systemctl reload nginx
curl -k -I https://localhost      # -k：接受自签名证书
别忘了 web.base.url

Odoo 生成邮件里的链接、门户链接时使用系统参数 web.base.url（第 14 章）。管理员登录时 Odoo 会自动把它更新为当前访问的地址。 用 HTTPS 域名以管理员身份登录一次，再到「设置 → 技术 → 参数 → 系统参数」确认它是 https://odoo.mycompany.com； 若不希望它再被自动修改，可以新增参数 web.base.url.freeze 设为 True。

维护：预发布环境与升级

服务器跑起来之后，迟早要做维护：更新 Odoo 代码以获得修复、升级自己的模块、安装新模块。这些操作都有风险， 所以最好先在一个预发布（staging）环境里演练一遍。

建立预发布环境

理想情况下预发布环境应该在一台单独的服务器上。一个简化但对大多数情况足够安全的做法，是把它放在生产服务器上，用不同的数据库和端口。

第一步：复制数据库。Odoo 20 的 odoo db duplicate 会连同 filestore 一起复制， --neutralize 选项还会「中和」副本：停用外发邮件服务器、计划任务、支付和第三方集成等，避免测试库给真实客户发邮件或扣款： 

sudo -u odoo /opt/odoo/env20/bin/odoo db -c /etc/odoo/odoo.conf \
    duplicate --force --neutralize odoo-prod odoo-stage
Odoo 15（书中写法）
dropdb odoo-stage
createdb --owner=odoo odoo-stage
pg_dump odoo-prod | psql -d odoo-stage
sudo su - odoo
cd ~/.local/share/Odoo/filestore/
cp -r odoo-prod odoo-stage
exit
# 还要自己写 SQL 停用邮件服务器……
Odoo 20
odoo db -c /etc/odoo/odoo.conf \
    duplicate --force --neutralize \
    odoo-prod odoo-stage

# 已有的库也可以单独中和：
odoo neutralize -c /etc/odoo/odoo.conf \
    -d odoo-stage

第二步：准备代码和配置。预发布环境需要一份独立的代码（这样才能先在这里试新代码）和一个使用不同端口的配置文件： 

sudo -u odoo -H bash
mkdir /opt/odoo/stage
cp -r /opt/odoo/odoo20 /opt/odoo/library /opt/odoo/stage/
python3 -m venv /opt/odoo/env-stage
/opt/odoo/env-stage/bin/pip install -r /opt/odoo/stage/odoo20/requirements.txt
/opt/odoo/env-stage/bin/pip install -e /opt/odoo/stage/odoo20
exit

[options]
addons_path = /opt/odoo/stage/odoo20/addons,/opt/odoo/stage/library
db_name = odoo-stage
dbfilter = ^odoo-stage$
http_port = 8080
gevent_port = 8073
logfile = /var/log/odoo/odoo-stage.log

更新代码

拉取新代码之前，先用 git tag 给当前版本打个标签，出问题时可以一步回到这里： 

sudo -u odoo -H bash
cd /opt/odoo/stage/odoo20
git tag --force 20-last-prod     # 记住当前版本
git pull
cd /opt/odoo/stage/library
git tag --force 20-last-prod
git pull
exit

Python 代码的改动需要重启服务才生效；数据文件（XML、CSV）的改动、新加的字段则需要升级模块。在预发布库上试一下： 

sudo -u odoo /opt/odoo/env-stage/bin/odoo module -c /etc/odoo/odoo-stage.conf \
    upgrade library_app library_member library_checkout library_portal
sudo -u odoo /opt/odoo/env-stage/bin/odoo -c /etc/odoo/odoo-stage.conf

然后用浏览器打开 http://服务器地址:8080（需要防火墙放行，或者用 SSH 端口转发 ssh -L 8080:localhost:8080 服务器），确认升级后一切正常。 如果有问题，用 git checkout 20-last-prod 回到之前的版本。

要不要升级所有模块？

Odoo 稳定分支（如 20.0）上的更新一般都是缺陷修复，通常重启服务就够了，不值得冒险升级所有模块。 需要时可以用 odoo module upgrade ... --outdated all 只升级「磁盘上版本号更新了」的模块；upgrade base 或 upgrade all 会升级全部模块，耗时也长得多。

升级生产环境

在预发布环境验证无误后，对生产环境做同样的代码更新。只需要重启的话，sudo systemctl restart odoo 就够了； 如果要升级模块，建议的流程是先备份、再停服、升级、启动： 

# 1. 备份：数据库 + filestore 打包成一个 zip
sudo -u odoo /opt/odoo/env20/bin/odoo db -c /etc/odoo/odoo.conf \
    dump odoo-prod /opt/odoo/backups/odoo-prod-$(date +%F).zip

# 2. 更新生产代码
sudo -u odoo git -C /opt/odoo/odoo20 tag --force 20-last-prod
sudo -u odoo git -C /opt/odoo/odoo20 pull
sudo -u odoo git -C /opt/odoo/library tag --force 20-last-prod
sudo -u odoo git -C /opt/odoo/library pull

# 3. 停服、升级、启动
sudo systemctl stop odoo
sudo -u odoo /opt/odoo/env20/bin/odoo module -c /etc/odoo/odoo.conf \
    upgrade library_app library_member library_checkout library_portal
sudo systemctl start odoo

万一升级后出了严重问题：停服，代码 git checkout 20-last-prod，再用 odoo db load --force 从刚才的 zip 恢复数据库，最后启动服务。

备份要定期做，而且要演练恢复

除了升级前的备份，还应该每天自动备份（比如用 systemd timer 或 cron 运行 odoo db dump），并把备份文件复制到另一台机器上。 没有演练过恢复的备份，不能算真正的备份——定期把备份恢复到预发布环境，就是最好的演练。

⇪ 大版本升级（比如 15 → 20）

本节讲的是同一大版本内的更新。跨大版本的升级需要迁移数据库结构和数据，不能只换代码：企业版用户可以使用 Odoo 官方的升级服务， 社区版通常借助 OCA 的 OpenUpgrade 项目。自定义模块的代码可以先用 odoo upgrade_code 命令自动完成一部分机械性的改写（比如 tree → list）， 剩下的再参照附录里的「15 → 20 变化速查」手工调整。

小结

  • 生产环境：Ubuntu 24.04 + PostgreSQL 16 + Python 3.12；用无特权的 odoo 系统用户运行，数据库账号不是超级用户。
  • 从源码安装（git clone -b 20.0 --depth=1 + 虚拟环境），便于更新和回滚。
  • 配置文件放在 /etc/odoo/odoo.conf；务必设置强 admin_passwd、list_db = False、dbfilter、proxy_mode，并只监听 127.0.0.1。
  • workers 启用多进程模式，经验值 2 × CPU + 1；WebSocket 由 gevent_port（8072）上的 gevent 进程处理。
  • systemd 服务让 Odoo 开机自启、崩溃自动重启；/web/version 可用作健康检查。
  • Nginx 反向代理：/websocket 转发到 8072 并升级连接，其余转发到 8069；设置 X-Forwarded-* 请求头；强制 HTTPS，推荐 Let's Encrypt 证书。
  • 维护：odoo db duplicate --neutralize 建立预发布库，git tag 记录版本，odoo module upgrade 升级模块，odoo db dump 备份。

动手练习

  1. 在一台虚拟机（或云服务器）上按本章完整部署一次 Odoo 20，并把本书的图书馆模块装进去。
  2. 用 ps aux | grep odoo 观察 worker 进程的数量，把 workers 改成 2 再重启，看看有什么变化。
  3. 打开浏览器开发者工具的「网络」面板，确认 /websocket 连接的状态码是 101 Switching Protocols。
  4. 写一个每天凌晨执行的 systemd timer（或 cron 任务），用 odoo db dump 备份生产库，并只保留最近 7 天的备份。
  5. 用 odoo db duplicate --neutralize 建一个预发布库，登录后到「设置 → 技术 → 外发邮件服务器」看看中和做了什么。
