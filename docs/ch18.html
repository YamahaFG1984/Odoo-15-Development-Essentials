第 18 章

多语言与翻译

Odoo 的源码和模块一律用英文书写，界面上的中文全部来自翻译文件。前面章节写的图书馆模块，切换成中文界面后依然满屏英文——因为我们还没给它做翻译。 这一章就来补上：搞清楚 Odoo 的翻译机制，把图书馆模块翻译成简体中文，并学会在代码里正确地标记可翻译文本。 即使你的用户只说中文，也值得这样做：代码保持英文，才能和 Odoo 生态里的其他模块、其他开发者顺畅协作。

本章目标

  • 为数据库启用简体中文，理解用户语言是怎么决定的
  • 知道哪些文本会被翻译，以及「模型术语」和「代码术语」两种机制的区别
  • 用 odoo i18n export 导出 .pot 模板，生成并翻译 zh_CN.po
  • 加载、覆盖、导入翻译，以及改了译文后需要做什么
  • 在 Python、JavaScript、QWeb 里正确标记可翻译文本，避开常见的坑
  • 让业务数据本身（比如书名）支持多语言

启用中文

一个数据库可以同时启用多种语言，每个用户在自己的偏好设置里选择界面语言。新建的数据库默认只有英语，启用其他语言有三种方式：

方式做法
建库时指定odoo db init library --language zh_CN，或者在数据库管理页面建库时选择语言
界面上「设置 → 语言」区域点「添加语言」，选择「Chinese (Simplified) / 简体中文」
命令行odoo i18n loadlang -c library.conf -d library -l zh_CN

启用一种语言时，Odoo 会为所有已安装的模块加载这种语言的翻译。之后再安装新模块，也会自动加载已启用语言的翻译。 然后到右上角的头像菜单 → 「我的偏好」，把语言改成简体中文，界面就切换过来了——除了我们自己写的模块。

ⓘ 语言代码 zh_CN

Odoo 用 POSIX 格式的语言代码：zh_CN（简体中文）、zh_TW（繁体中文，台湾）、zh_HK（繁体中文，香港）、en_US、fr_FR…… 翻译文件就以它命名，比如 zh_CN.po。在开发者模式下打开「设置 → 翻译 → 语言」可以查看所有可用语言的代码。

哪些文字会被翻译

好消息是：大部分文字不用你做任何事就是「可翻译的」，Odoo 在导出翻译时会自动把它们收集起来。需要你手动标记的，只有写在 Python 和 JavaScript 代码里的字符串：

两种翻译，两种存放方式

这些文字被翻译后，存放的位置却不一样。理解这一点，才能明白「为什么改了译文有时要升级、有时要重启」：

⇪ ir.translation 已经不存在了

书中介绍的 Odoo 15 把所有译文存在一张 ir_translation 表里。Odoo 16 起这张表被取消：模型术语改成直接存在各自字段的 JSONB 列中， 代码术语改为运行时读取 .po 文件。网上提到 ir.translation 的老代码，在 Odoo 20 上都不能用了。

导出翻译模板

翻译的起点是一个 .pot 文件（PO Template）：它列出了模块里所有需要翻译的英文原文，但译文都是空的。 Odoo 20 提供了 odoo i18n 命令来生成它。模块必须已经安装在指定的数据库里： 

(env20) $ odoo i18n export -c ~/work20/library.conf -d library library_app

命令会直接把文件写进模块目录：library_app/i18n/library_app.pot（i18n 目录不存在时会自动创建）。 再用 -l 指定语言，生成中文的 .po 文件： 

(env20) $ odoo i18n export -c ~/work20/library.conf -d library library_app -l zh_CN
# 生成 library_app/i18n/zh_CN.po

(env20) $ odoo i18n export -c ~/work20/library.conf -d library library_app library_member -l pot zh_CN
# 一次导出两个模块的模板和中文译文，各自写进自己的 i18n 目录
模块名要写在 -l 前面

-l 后面可以跟多个语言代码，它会把后面所有不带 - 的词都当成语言。写成 -l zh_CN library_app， library_app 就被当成了一种语言，命令随即报错说缺少模块参数。所以把模块名放在前面，-l 放在最后。

导出某种语言时，这种语言必须已经启用；文件里已经有的译文（数据库里的、或者原来 .po 文件里的）会一并带出来，新出现的原文则是空的。 所以以后代码有了新的文字，重新导出一次，再把空着的补上就行了。

💡 也可以在界面上导出

开发者模式下，「设置 → 翻译 → 导入 / 导出 → 导出翻译」会打开一个向导：选择语言、文件格式（PO、CSV 等）和模块，然后下载文件。 对应的「导入翻译」可以把 .po 文件上传回来。适合没有服务器命令行权限的场合。

读懂 .po 文件

.po 是 GNU gettext 的标准格式，纯文本，由一个个条目组成。打开导出的 zh_CN.po：

# Translation of Odoo Server.
# This file contains the translation of the following modules:
# 	* library_app
#
msgid ""
msgstr ""
"Project-Id-Version: Odoo Server 20.0\n"
"POT-Creation-Date: 2026-10-22 14:57+0000\n"
"Content-Type: text/plain; charset=UTF-8\n"
...

#. module: library_app
#: model:ir.model,name:library_app.model_library_book
msgid "Book"
msgstr "图书"

#. module: library_app
#: model:ir.model.fields,field_description:library_app.field_library_book__name
msgid "Title"
msgstr "书名"

#. module: library_app
#: model_terms:ir.ui.view,arch_db:library_app.view_form_book
msgid "Check ISBN"
msgstr "检查 ISBN"

#. module: library_app
#. odoo-python
#: code:addons/library_app/models/library_book.py:0
msgid "Please provide an ISBN for %s"
msgstr "请为《%s》填写 ISBN"

出处（#: 行）的前缀表明了这是哪一类术语，正好对应图 18-2 的两种机制：

前缀含义改了之后
model:某条记录的某个字段的整个值，比如模型名、字段标签、菜单名升级模块
model_terms:某个大字段里的一段文字，最常见的是视图的 arch_db升级模块
code:Python（#. odoo-python）或 JS（#. odoo-javascript）代码里标记的字符串重启服务器

翻译时的注意事项

  • 占位符原样保留：%s、%(name)s、%d 一个都不能少，名字也不能改。顺序可以按中文习惯调整——这正是推荐用命名占位符 %(name)s 的原因。
  • HTML 和 QWeb 标签保留：视图里的一段文字如果夹着 <strong> 之类的标签，原文里会带着它们，译文里也要保留。
  • 同一个原文只翻译一次：多处用到的相同原文会合并成一个条目，出处有多行。
  • 可以用文本编辑器直接改，也可以用 Poedit 这类专门的翻译工具，它会检查占位符是否一致。

加载翻译

.po 文件放在模块的 i18n/ 目录里，就会被 Odoo 自动使用，不需要写进清单。具体在什么时候生效：

情况会发生什么
安装模块为所有已启用的语言加载模型术语
启用一种新语言为所有已安装的模块加载这种语言的模型术语
升级模块（-u）加载模型术语，但不覆盖数据库里已经有的译文
升级时加 --i18n-overwrite用 .po 文件里的译文覆盖已有的译文
重启服务器代码术语从 .po 文件重新读取

所以，修改了 zh_CN.po 里已有的译文之后，要这样让它生效：

(env20) $ odoo -c ~/work20/library.conf -d library -u library_app --i18n-overwrite

-u 会顺带重启服务器，所以代码术语也一起更新了。如果只是想把一个 .po 文件（不一定在模块目录里）导入数据库，可以用 i18n import： 

(env20) $ odoo i18n import -c ~/work20/library.conf -d library -l zh_CN -w library_app/i18n/zh_CN.po
# -w 表示覆盖已有的译文
为什么默认不覆盖

用户可能已经在界面上把某个译文改成了更符合自己公司习惯的说法。如果每次升级都覆盖，这些修改就会丢失。 所以只有你明确要求（--i18n-overwrite 或 -w）时，Odoo 才会用文件里的译文覆盖数据库。

语言的回退顺序

Odoo 为一种语言加载翻译时，会先加载它的「基础语言」文件，再加载具体地区的文件，后者覆盖前者。这让地区变体只需要翻译和基础语言不同的部分：

在 Python 里标记文本

给用户看的字符串（报错消息、通知、默认值……）都要用 self.env._() 包起来：

    def button_check_isbn(self):
        for book in self:
            if not book.isbn:
                raise ValidationError(
                    self.env._("Please provide an ISBN for %s", book.name))
            if not book._check_isbn():
                raise ValidationError(
                    self.env._("%s ISBN is invalid", book.isbn))
        return True

self.env._() 用的是当前环境的语言（也就是当前用户的语言）。第一个参数是英文原文，后面的参数会被填进占位符——先翻译、后填值，顺序很重要：

✗ 错误：先拼好再翻译
self.env._(f"Please provide an ISBN for {book.name}")
self.env._("Please provide an ISBN for %s" % book.name)
self.env._("Please provide ") + self.env._("an ISBN")
✓ 正确：原文固定，参数另传
self.env._("Please provide an ISBN for %s", book.name)
self.env._("%(title)s by %(author)s",
           title=book.name, author=author.name)
self.env._("Please provide an ISBN")

左边前两种写法，传给 _() 的已经是「Please provide an ISBN for Odoo Development」这样带着书名的字符串， .po 文件里不可能有这么一条原文，所以永远找不到译文，而且导出工具也认不出它。第三种把一句话拆成碎片，译者无法按中文语序组织句子。

模块级的常量：用延迟翻译

self.env._() 需要知道「当前用户的语言」，所以只能在方法里调用。如果要在模块顶层定义一些可翻译的常量（比如选择项之外的提示文字表）， 要用延迟翻译：定义时只记下原文，真正用到时才按当时的语言翻译： 

from odoo.tools import LazyTranslate

_lt = LazyTranslate(__name__)

STATE_HINTS = {
    "new": _lt("Waiting for approval"),
    "done": _lt("Returned to the library"),
}
ⓘ 字段标签不需要标记

fields.Char("Title")、help="..."、selection=[("new", "New")] 里的文字会被自动收集，不要再包一层 _()。 选择项只翻译标签（"New"），键（"new"）是存进数据库的技术值，永远不翻译。

⇪ _() 和 self.env._()

书中使用 from odoo import _，然后写 _("...")。这个函数要通过检查调用栈去「猜」当前的语言和模块，既慢又不总是可靠。 Odoo 18 起推荐写 self.env._("...")，直接从环境里拿语言。_ 仍然可以用，但新代码请用 self.env._。

在 JavaScript 和模板里

前端代码里用 _t，用法和 Python 一样：

import { _t } from "@web/core/l10n/translation";

this.notification.add(_t("The book %s has been returned.", book.name), {
    type: "success",
});

OWL 模板、视图、报表和网页的 QWeb 模板里的文字自动可翻译，什么都不用做。反过来，如果某段文字不应该被翻译（比如示例代码、品牌名）， 在元素上加 t-translation="off"，比如一个固定的英文书名： 

<p t-translation="off">Odoo Development Essentials, 5th Edition</p>

让业务数据也支持多语言

上面说的都是界面文字。如果数据本身也需要多语言——比如面向多国读者的图书馆，书的简介要有中英文两个版本——在字段上加 translate=True（第 6 章）。比如给图书加一个简介字段： 

    description = fields.Html("Description", translate=True)

升级模块后，表单里这个字段的输入框右侧会出现一个显示语言代码的小按钮，点开就能分别填写每种语言的内容。用户看到的是自己语言的版本，没有译文时退回英文。

不要给编号、代码类字段开翻译

ISBN、内部编码、邮箱这类字段在所有语言里都一样，开了翻译只会让数据混乱。translate=True 只用于真正需要按语言区分的描述性文字。

翻译工作流

ⓘ 官方和社区的翻译平台

Odoo 官方模块的翻译由社区在 Odoo 的 Weblate 翻译平台上协作完成，base 模块 zh_CN.po 的文件头里就能看到翻译者的名字。 OCA 的模块也有自己的翻译平台，翻译会被自动提交回各个仓库。如果你发现官方中文译文有不妥之处，可以去这些平台上提交修改。

不要提交 en.po

英语是原文语言，不需要翻译文件。OCA 的代码检查甚至会拒绝包含 i18n/en.po 的提交（第 19 章）。

小结

  • 代码一律写英文；界面文字通过 i18n/ 目录里的 .po 文件翻译，文件以语言代码命名，如 zh_CN.po。
  • 字段定义、视图、QWeb 模板、数据记录里的文字自动可翻译；Python 用 self.env._()、JS 用 _t() 手动标记。
  • 模型术语在安装 / 升级时写进数据库（JSONB），代码术语在运行时从 .po 读取：前者改了要升级，后者改了要重启。
  • odoo i18n export 导出 .pot 和 .po；odoo i18n import 导入；odoo i18n loadlang 启用语言。
  • 升级默认不覆盖已有译文，需要时加 --i18n-overwrite。
  • 先翻译后填值：原文里用占位符，参数另外传，不要用 f-string 或字符串拼接。
  • 业务数据需要多语言时用 translate=True，编号类字段不要开。

动手练习

  1. 为你的数据库启用简体中文，把自己的界面语言切换过去，看看图书馆模块现在是什么样子。
  2. 导出 library_app 的 zh_CN.po，翻译所有条目，用 -u library_app --i18n-overwrite 加载，再检查界面。
  3. 点「Check ISBN」按钮触发报错，确认报错消息也变成了中文。如果没有，想想是不是忘了重启。
  4. 在按钮方法里故意写一个 f-string 版本的 _()，重新导出，观察 .po 文件里出现了什么（或者没出现什么）。
  5. 给 library_member 模块也做一份中文翻译，并把两个模块的 i18n/ 目录提交到 Git。
