第 20 章

综合实战：贸易公司进销存

前面十几章我们一直在建设图书馆系统，每一步都有现成的代码可以照着敲。这一章换一种方式：给你一个真实的业务场景和一份需求清单， 由你自己决定哪些用标准功能配置、哪些需要写代码，然后动手实现。每个开发任务都附有思路提示和折叠起来的参考答案—— 先自己做，卡住了再展开看。做完这个项目，你就走完了一次真实的 Odoo 实施。

本章目标

  • 把业务需求拆解成「标准配置」和「定制开发」两部分（差异分析）
  • 用销售、采购、库存、开票四个标准应用搭起贸易公司的主流程
  • 开发扩展模块：新模型、继承已有模型和视图、计算字段、重写业务方法、权限、报表
  • 为关键业务规则编写自动化测试
  • 按验收清单从询价到收款走通全流程

项目背景：鑫达商贸

鑫达商贸（虚构）是一家 20 人左右的贸易公司，从几家工厂采购手机配件和数码周边（数据线、充电器、转接头、移动电源……）， 存放在自己的一个仓库里，再批发给各地的零售店和企业客户。公司目前用 Excel 管理库存、用微信接单，问题越来越多：

  • 销售员给客户报价时随意打折，月底一算毛利才发现亏了；
  • 库存数字总是对不上，经常卖出去了才发现没货，临时找工厂补货；
  • 仓库发货靠手写清单，物流公司要货物重量时又得现称；
  • 老板想知道「大客户和小客户各贡献了多少销售额」，没人答得上来。

差异分析：配置还是开发

拿到需求清单后，有经验的 Odoo 顾问做的第一件事，是逐条判断：标准功能能不能满足？能配置解决的绝不写代码—— 代码要维护、要测试、每次升级 Odoo 都要迁移，而标准功能由 Odoo 替你维护。这个过程叫差异分析（fit-gap analysis）。

编号需求结论怎么做
R1管理产品目录，记录进价、售价、重量、条码标准产品；勾选「跟踪库存」
R2客户和供应商档案、付款条件标准联系人、付款条款
R3不同客户用不同的价格标准销售设置里启用价格表，给客户指定价格表
R4库存低于安全量时自动补货标准产品的供应商 + 「购买」路线 + 补货规则（最小 / 最大库存）
R5销售员只能看自己的客户和订单标准权限组「销售：用户（仅自己的单据）」
R6控制客户欠款标准开票设置里启用客户信用额度，在客户上设置额度
R7客户分为 A / B / C 三级，每一级有自己的折扣上限和大单金额开发新模型 + 继承联系人
R8超过折扣上限或超过大单金额的订单，必须由销售经理批准才能确认开发继承销售订单：计算字段、审批按钮、拦截确认
R9发货时打印装箱单，列出每样货物和总重量开发库存调拨上的 QWeb 报表
R10按客户等级统计销售额开发 + 标准订单上加一个存储的等级字段，再用标准的分组和透视表
先配置，后开发

很多新手一上来就写代码，结果花两周开发了一个「审批流」，后来发现标准功能稍加配置就能做到。 动手之前，先在一个装了演示数据的库里把标准流程完整走一遍，确认标准功能真的满足不了，再开始写代码。

第一阶段：标准配置

建库与安装应用

(env20) $ odoo db -c ~/work20/trading.conf init trading --language zh_CN
(env20) $ odoo module install -c ~/work20/trading.conf -d trading sale_management purchase stock account

trading.conf 可以从第 2 章的配置文件复制一份，把 addons_path 改成包含 trading_custom 所在的目录。 注意 odoo db 的 -c 要写在子命令 init 前面，而 odoo module 的写在后面。 用 Docker 环境（第 17 章）的话，在命令前面加 docker compose exec odoo，并省略 -c。account 在社区版里显示为「开票」应用。 安装销售和库存后，桥接模块 sale_stock（确认销售订单时自动生成发货单）会自动安装；采购和库存之间的 purchase_stock 也一样。

💡 先在演示库里试

另建一个 --with-demo 的库，用演示数据把销售、采购、发货、开票都点一遍，熟悉标准流程之后再配置正式的库。

逐条配置

  1. 公司信息（设置 → 公司）：公司名称、地址、币种（人民币）、Logo。这些会出现在报价单、发票和后面我们自己做的装箱单上。
  2. 产品（R1）：新建几个产品，类型选「货物」并勾选跟踪库存；填写销售价格、成本、重量和条码。在「采购」页签添加供应商及其报价；在「库存」页签勾选购买路线。
  3. 客户与供应商（R2）：在联系人里建几家公司，区分客户和供应商（在销售和采购单据里用过，它们就会自动出现在对应的列表中）；在「销售和采购」页签设置付款条款。
  4. 价格表（R3）：在销售设置里启用「价格表」，建一个「批发价」价格表（比如全场 9 折），指定给部分客户。
  5. 补货规则（R4）：在库存的「补货」界面给常卖的产品设置最小库存和最大库存。库存低于最小值时，Odoo 会自动按产品的供应商生成采购询价单。
  6. 用户与权限（R5）：建几个用户，销售员设为「销售：用户（仅自己的单据）」，销售经理设为「销售：管理员」，再分别给采购、库存、开票人员相应的权限。
  7. 信用额度（R6）：在开票设置里启用客户信用额度，在客户的「开票」相关页签设置额度。超过额度的订单会在确认时显示提醒。
ⓘ 菜单位置找不到？

Odoo 各版本的菜单布局时有调整，如果某个选项没在上面说的位置，用设置页面顶部的搜索框搜关键词（比如「价格表」「信用」）通常最快。

配置完成后，按图 20-2 的流程走一遍：报价 → 确认 → 自动生成采购 → 收货 → 发货 → 开票 → 收款。这条主线跑通了，第一阶段就完成了。

任务 1：客户分级（R7）

R7新建「客户等级」模型，在销售的配置菜单里维护；在联系人表单上可以给公司选择等级。

  • 模型：等级名称、排序、折扣上限（%）、大单金额（0 表示不限）。（第 6 章）
  • 访问规则：所有内部用户可读（仓管员打开联系人时也要显示等级名），销售管理员可增删改。（第 3 章）
  • 预置 A、B、C 三个等级，放在 noupdate 数据里，免得升级时覆盖客户的调整。（第 5 章）
  • 继承联系人表单，把等级字段放进「销售和采购」页签的「销售」分组；只在顶层公司上显示。（第 4 章）

任务 2：订单审批（R8）

R8订单的任意一行折扣超过客户等级的折扣上限，或者未税金额超过大单金额，订单就进入「待审批」；销售经理批准后才能确认。批准以后如果金额又增加了，需要重新审批。

  • customer_tier_id：关联字段，取 partner_id.commercial_partner_id.customer_tier_id，store=True，后面的分析要用它分组。（第 6 章）
  • approval_state：存储的计算字段，依赖金额、行折扣、等级、批准信息和订单状态；存储才能在列表里筛选「待审批」。
  • approval_reason：不存储的计算字段，用文字说明为什么需要审批，显示在表单顶部。
  • action_approve()：只有销售管理员能执行；记录批准人、时间和批准时的金额，并在消息区留言。（第 8 章）
  • 拦截确认：不要重写整个 action_confirm()。读一读它的源码——它会对每张订单调用 _confirmation_error_message()，返回了消息就报错。重写这个小方法就够了。
  • 界面：「批准」按钮、待审批提示条、列表里的审批状态徽标、搜索里的「待审批」筛选和「按客户等级」分组。（第 10 章）
💡 找到合适的扩展点

扩展别人的业务逻辑时，先去源码里找「钩子」：Odoo 的开发者经常把一大段逻辑拆出一些小方法，专门留给别人重写。 在 addons/sale/models/sale_order.py 里搜 def action_confirm，就能看到 _confirmation_error_message 这个钩子。重写的范围越小，和其他模块冲突的可能越小，升级时要改的也越少。

参考答案：sale_order.py 
from odoo import api, fields, models
from odoo.exceptions import AccessError

APPROVAL_FIELDS = {"approved_by_id", "approved_date", "approved_amount"}


class SaleOrder(models.Model):
    _inherit = "sale.order"

    customer_tier_id = fields.Many2one(
        related="partner_id.commercial_partner_id.customer_tier_id",
        store=True,
        string="Customer Tier",
    )
    approval_state = fields.Selection(
        [
            ("not_required", "Not Required"),
            ("pending", "Waiting Approval"),
            ("approved", "Approved"),
        ],
        compute="_compute_approval_state",
        store=True,
        tracking=True,
    )
    approval_reason = fields.Text(compute="_compute_approval_reason")
    approved_by_id = fields.Many2one("res.users", readonly=True, copy=False)
    approved_date = fields.Datetime(readonly=True, copy=False)
    approved_amount = fields.Float(readonly=True, copy=False)

    @api.depends(
        "state",
        "amount_untaxed",
        "order_line.discount",
        "customer_tier_id",
        "approved_by_id",
        "approved_amount",
    )
    def _compute_approval_state(self):
        for order in self:
            if order.state not in ("draft", "sent"):
                # 已确认或已取消的订单不再参与审批
                order.approval_state = "approved" if order.approved_by_id else "not_required"
            elif not order._get_approval_reasons():
                order.approval_state = "not_required"
            elif order.approved_by_id and order.amount_untaxed <= order.approved_amount:
                order.approval_state = "approved"
            else:
                order.approval_state = "pending"

    @api.depends("amount_untaxed", "order_line.discount", "customer_tier_id")
    def _compute_approval_reason(self):
        for order in self:
            order.approval_reason = "\n".join(order._get_approval_reasons())

    def write(self, vals):
        # 只读字段只是界面上的限制；通过 API 直接写入时，在这里把关
        if (
            APPROVAL_FIELDS & vals.keys()
            and not self.env.su
            and not self.env.user.has_group("sales_team.group_sale_manager")
        ):
            raise AccessError(self.env._("Only sales managers can approve orders."))
        return super().write(vals)

    def action_approve(self):
        if not self.env.user.has_group("sales_team.group_sale_manager"):
            raise AccessError(self.env._("Only sales managers can approve orders."))
        for order in self.filtered(lambda o: o.approval_state == "pending"):
            order.write({
                "approved_by_id": self.env.user.id,
                "approved_date": fields.Datetime.now(),
                "approved_amount": order.amount_untaxed,
            })
            order.message_post(body=self.env._("Approved by %s.", self.env.user.name))
        return True

    def _confirmation_error_message(self):
        error = super()._confirmation_error_message()
        if not error and self.approval_state == "pending":
            error = self.env._(
                "Order %(order)s needs a sales manager's approval before it "
                "can be confirmed:\n%(reasons)s",
                order=self.name,
                reasons=self.approval_reason,
            )
        return error

    def _get_approval_reasons(self):
        self.ensure_one()
        tier = self.customer_tier_id
        if tier:
            max_discount, limit = tier.max_discount, tier.approval_amount
        else:
            max_discount = 0.0
            limit = self.env["ir.config_parameter"].sudo().get_float(
                "trading_custom.default_approval_amount"
            )
        reasons = []
        lines = self.order_line.filtered(lambda line: not line.display_type)
        if any(line.discount > max_discount for line in lines):
            reasons.append(
                self.env._("A line has a discount above %(max)s%%.", max=max_discount)
            )
        if limit and self.amount_untaxed > limit:
            reasons.append(
                self.env._("The untaxed amount exceeds %(limit)s.", limit=limit)
            )
        return reasons

几个值得注意的地方：

  • 状态是算出来的：批准只是记下「谁、何时、批了多少钱」，approval_state 由计算方法根据这些事实推导。金额增加超过 approved_amount 时，状态自动回到 pending，不需要在 write() 里写一堆「如果……就重置」。
  • display_type 不为空的行是分节标题和备注，不是真正的商品行，要排除掉。
  • get_float() 要读系统参数，普通销售员没有这个权限，所以用 sudo()——这正是「只在需要的那一小段代码里提权」的例子。
  • 按钮上的 groups 只是把按钮藏起来，真正的安全检查在服务器端：action_approve() 和 write() 都会检查组。不要依赖界面来保证安全。
  • tracking=True：审批状态的每次变化都会自动记录在订单的消息区里，谁在什么时候让订单进入了待审批一目了然。

任务 4：按客户等级分析（R10）

R10老板要看每个客户等级的订单金额和数量。

这个需求在任务 2 里其实已经完成了一大半：订单上的 customer_tier_id 是存储的关联字段，可以分组；搜索视图里也加了「按客户等级」分组。 打开销售订单列表，选择分组「Customer Tier」，每组的金额合计就出来了；切换到透视表视图，把等级放在行、订单日期的月份放在列，就是一张月度分级销售表。

ⓘ 为什么一定要 store=True

分组和透视表是在数据库里用 SQL 的 GROUP BY 完成的，只有存在表里的列才能参与。不存储的关联字段每次读取时临时计算，没法分组。 存储的代价是：客户换了等级，历史订单上的等级也会跟着变，因为关联字段会随源字段一起更新。如果老板想看的是「下单当时」的等级，就要改成一个普通字段，在创建订单时赋值。这是一个值得和客户讨论的业务问题。

from odoo.exceptions import AccessError, UserError
from odoo.fields import Command
from odoo.tests import TransactionCase, tagged


@tagged("post_install", "-at_install")
class TestSaleApproval(TransactionCase):
    @classmethod
    def setUpClass(cls):
        super().setUpClass()
        cls.tier = cls.env["trading.customer.tier"].create({
            "name": "Test Tier",
            "max_discount": 5.0,
            "approval_amount": 10000.0,
        })
        cls.customer = cls.env["res.partner"].create({
            "name": "Test Retailer",
            "is_company": True,
            "customer_tier_id": cls.tier.id,
        })
        cls.product = cls.env["product.product"].create({
            "name": "USB-C Cable",
            "list_price": 100.0,
        })
        cls.salesman = cls._create_user("sam", "sales_team.group_sale_salesman")
        cls.manager = cls._create_user("mia", "sales_team.group_sale_manager")

    @classmethod
    def _create_user(cls, login, group_xmlid):
        return cls.env["res.users"].create({
            "name": login.title(),
            "login": login,
            "group_ids": [Command.set([cls.env.ref(group_xmlid).id])],
        })

    def _create_order(self, discount=0.0, qty=10):
        return self.env["sale.order"].create({
            "partner_id": self.customer.id,
            "order_line": [Command.create({
                "product_id": self.product.id,
                "product_uom_qty": qty,
                "discount": discount,
            })],
        })

    def test_small_order_needs_no_approval(self):
        order = self._create_order(discount=3.0)
        self.assertEqual(order.approval_state, "not_required")
        order.action_confirm()
        self.assertEqual(order.state, "sale")

    def test_high_discount_blocks_confirmation(self):
        order = self._create_order(discount=8.0)
        self.assertEqual(order.approval_state, "pending")
        with self.assertRaises(UserError):
            order.action_confirm()

    def test_salesman_cannot_approve(self):
        order = self._create_order(discount=8.0)
        with self.assertRaises(AccessError):
            order.with_user(self.salesman).action_approve()

    def test_manager_approves_then_confirms(self):
        order = self._create_order(discount=8.0)
        order.with_user(self.manager).action_approve()
        self.assertEqual(order.approval_state, "approved")
        self.assertEqual(order.approved_by_id, self.manager)
        order.action_confirm()
        self.assertEqual(order.state, "sale")

    def test_bigger_amount_needs_new_approval(self):
        order = self._create_order(discount=8.0)
        order.with_user(self.manager).action_approve()
        order.order_line.product_uom_qty = 200      # 金额远超批准时的金额
        self.assertEqual(order.approval_state, "pending")

BASE_URL = os.environ["ODOO_URL"] + "/json/2"

def call(model, method, **params):
    r = requests.post(f"{BASE_URL}/{model}/{method}", headers=HEADERS, json=params, timeout=30)

    return r.json()

小结

  • 真实项目从业务出发：先认识用户和流程，再逐条做差异分析，能配置的不开发。
  • 贸易公司的主流程完全由标准的销售、采购、库存、开票应用覆盖；定制部分集中在一个扩展模块里。
  • 扩展已有业务逻辑时，在源码里找最小的钩子（这里是 _confirmation_error_message），而不是重写一整个大方法。
  • 状态尽量「算」出来（存储的计算字段），而不是到处手动维护，数据就不会自相矛盾。
  • 界面上的 groups 和 readonly 只是体验，安全检查必须放在服务器端。
  • 关键业务规则写成测试；验收时用不同角色的账号亲手走一遍全流程。
