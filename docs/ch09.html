第 9 章

外部 API

Odoo 服务器对外开放了一套 API：Web 客户端能做的事，别的程序也能做。用它可以写脚本批量导入导出数据， 也可以把 Odoo 和其他系统（网店、仓储系统、BI 工具……）连接起来，让 Odoo 充当它们的「后端」。 这一章先探索 API，再用 Python 写一个管理书目的命令行小程序。

本章目标

  • 理解 Odoo 外部 API 的现状：新的 JSON-2 API 与已废弃的 XML-RPC / JSON-RPC
  • 创建 API Key，用 HTTP 请求调用任意模型的公开方法
  • 掌握 search_read、read、create、write、unlink 等常用调用
  • 理解「每次调用一个事务」带来的设计约束
  • 写一个分层的命令行客户端，并能在新旧两种协议之间切换
⇪ 这一章和原书差别最大

原书全部使用 XML-RPC（/xmlrpc/2/common、/xmlrpc/2/object）和基于 JSON-RPC 的 OdooRPC 库。 Odoo 19 推出了全新的 JSON-2 API，同时宣布：/xmlrpc、/xmlrpc/2、/jsonrpc 三个端点已废弃， 其中数据库服务（db）在 Odoo 20 已经移除，模型调用服务（common、object）计划在 Odoo 22（2028 年秋）移除。 在 Odoo 20 上调用旧端点仍然可以工作，但每次调用都会在服务器日志里留下一条废弃警告。新项目请直接使用 JSON-2。

学习项目：书目命令行工具

我们要写一个以 Odoo 为后端的命令行（CLI）小程序，功能刻意保持简单，好把注意力放在「怎么和 Odoo 对话」上：

  • 按书名搜索并列出书
  • 添加新书
  • 修改书名
  • 删除书
$ python3 library.py add "Moby-Dick"
Book added with ID 3 for title Moby-Dick.
$ python3 library.py list "moby"
3 Moby-Dick
$ python3 library.py set 3 "Moby Dick"
Title of Book ID 3 set to Moby Dick.
$ python3 library.py del 3
Book with ID 3 was deleted.

客户端用 Python 写，这样不必再学一门语言。但 JSON-2 就是普通的「HTTP + JSON」，任何语言（JavaScript、Go、Java、PHP、甚至 curl）都能调用，原理完全一样。 客户端机器上需要 Python 3 和 requests 库： 

python3 --version
pip install requests
ⓘ Windows 一体化安装包的用户

Odoo 的 Windows 安装包里内嵌了一个 Python，但它不对系统开放。写客户端程序需要另外安装 Python（可以从 Microsoft Store 或 python.org 安装）。

JSON-2 API 入门

JSON-2 的设计非常直接：把模型名和方法名放进 URL，把参数放进 JSON 请求体，用 API Key 认证。

第一步：创建 API Key

JSON-2 不接受用户名和密码，只认 API Key：

  1. 登录 Odoo，点右上角头像 → 我的偏好（Preferences）。
  2. 打开 安全（Security）标签页，在 API Keys 一栏点 Create API Key，按提示确认密码。
  3. 填写描述（比如「library-cli」）和有效期，点 Generate Key。
  4. 立即复制显示出来的密钥 —— 它只显示这一次，之后无法再查看。
⚠ 像对待密码一样对待 API Key
  • 不要写进代码、不要提交到 Git。放在环境变量或专门的密钥管理工具里。
  • 密钥最长有效期为 3 个月，需要定期轮换。交互式试用时设短一点（比如一天）。
  • 密钥泄露或丢失，立刻在同一页面删除它，再生成新的。
  • 给系统集成用的密钥，最好属于一个专门的机器人用户：只授予它需要的最小权限，并把它的登录密码留空（禁止用账号密码登录）。审计字段里也能清楚地看出哪些修改来自集成。

在终端里把密钥放进环境变量，后面的例子都从这里读取：

export ODOO_URL="http://localhost:8069"
export ODOO_DB="library"
export ODOO_API_KEY="粘贴你的密钥"

第二步：确认能连通

服务器版本信息不需要认证。旧 API 里的 common.version()，现在是一个普通的 HTTP 端点： 

$ curl -s $ODOO_URL/web/version
{"version_info": [20, 0, 0, "final", 0, ""], "version": "20.0"}

第三步：第一次调用

打开 Python 交互式命令行：

>>> import os, requests
>>> BASE_URL = os.environ["ODOO_URL"] + "/json/2"
>>> headers = {
...     "Authorization": "bearer " + os.environ["ODOO_API_KEY"],
...     "X-Odoo-Database": os.environ["ODOO_DB"],
...     "User-Agent": "library-cli",
... }
>>> r = requests.post(f"{BASE_URL}/res.users/search_count", headers=headers, json={"domain": []})
>>> r.raise_for_status()
>>> r.json()
5

requests.post(..., json=...) 会自动把字典编码成 JSON 并设置 Content-Type: application/json。 调用成功时返回 200 状态码，响应体就是方法返回值的 JSON。

ⓘ 什么时候需要 X-Odoo-Database

一个 Odoo 服务器上有多个数据库、并且没有配置按域名选择数据库（dbfilter）时，必须用这个请求头告诉服务器用哪个库。 只有一个库，或者每个库有自己的域名时，可以省略。

谁在调用？

旧 API 先调用 authenticate() 拿到用户 ID，之后每次调用都要传数据库名、用户 ID 和密码。JSON-2 不需要这些：用户由 API Key 决定。 想知道当前是谁，可以调用 res.users 的 context_get： 

>>> requests.post(f"{BASE_URL}/res.users/context_get", headers=headers, json={}).json()
{'lang': 'en_US', 'tz': 'Europe/Brussels', 'uid': 2}

常用调用

所有公开的模型方法都可以调用 —— 也就是名字不以下划线开头、没有被标记为 @api.private 的方法。 这包括 ORM 的通用方法，也包括你自己写的业务方法（比如第 3 章的 button_check_isbn）。

为了少写重复代码，先定义一个小函数：

>>> def call(model, method, **params):
...     r = requests.post(f"{BASE_URL}/{model}/{method}", headers=headers, json=params)
...     r.raise_for_status()
...     return r.json()

查询：search、read、search_read

服务器端代码用 search() 得到记录集，再读取字段。但记录集对象没法通过网络传输，所以外部调用时： search 返回的是 ID 列表；读取数据要用 read，它返回的是字典列表。 

>>> call("res.users", "search", domain=[("login", "=", "admin")])
[2]
>>> call("res.users", "read", ids=[2], fields=["login", "name", "company_id"])
[{'id': 2, 'login': 'admin', 'name': 'Mitchell Admin', 'company_id': [1, 'YourCompany']}]

注意多对一字段的值：它是一个 [ID, 显示名称] 的二元组，比如 [1, 'YourCompany']。对多字段则是 ID 列表。

「先搜索、再读取」需要两次请求，而且两次请求之间数据可能被别人改掉（比如某条记录被删了，read 就会报错）。 search_read 把两步合成一步，在同一个事务里完成，这是读取数据最常用的方法： 

>>> call("res.users", "search_read",
...      domain=[("login", "=", "admin")],
...      fields=["login", "name"])
[{'id': 2, 'login': 'admin', 'name': 'Mitchell Admin'}]
search_read 参数含义
domain域表达式（JSON 里元组写成数组）
fields要读取的字段列表。务必写明：不写会读取全部字段，可能触发大量计算、传输大量数据
offset / limit分页
order排序，如 "name desc"

写入：create、write、unlink

>>> ids = call("res.partner", "create", vals_list=[{"name": "Packt Pub"}])
>>> ids
[49]
>>> call("res.partner", "write", ids=ids, vals={"name": "Packt Publishing"})
True
>>> call("res.partner", "read", ids=ids, fields=["name"])
[{'id': 49, 'name': 'Packt Publishing'}]
>>> call("res.partner", "unlink", ids=ids)
True
>>> call("res.partner", "read", ids=ids, fields=["name"])
[]

JSON-2 里所有参数都按名字传，名字就是 Python 方法签名里的参数名：create(vals_list)、write(vals)、read(fields)…… create 返回的是新建的记录集，JSON-2 自动把记录集转换成 ID 列表，所以得到 [49]。 不知道参数名时，去看方法的源码，或者看下面介绍的 /doc 页面。

上下文与错误

上下文通过请求体里的 context 键传入，比如读取中文的翻译值、或者连已归档的记录一起搜索：

>>> call("library.book", "search_read",
...      context={"lang": "zh_CN", "active_test": False},
...      domain=[], fields=["name", "active"])

出错时，服务器返回 4xx / 5xx 状态码，响应体是一个描述错误的 JSON 对象：

HTTP/1.1 401 Unauthorized
{
  "name": "werkzeug.exceptions.Unauthorized",
  "message": "Invalid apikey",
  "arguments": ["Invalid apikey", 401],
  "context": {},
  "debug": "Traceback (most recent call last): ..."
}

name 是 Python 异常的完整类名，message 是错误信息。业务代码里抛出的 UserError、ValidationError、权限不足的 AccessError 都会这样返回给调用方。客户端应该检查状态码，并把 message 展示给用户。

动态 API 文档：/doc

Odoo 20 自带一个 api_doc 模块（自动安装），在 http://localhost:8069/doc 提供根据当前数据库生成的 API 文档： 列出所有模型、字段、可调用的方法及其参数，还能直接在页面上试着调用，并生成 Python、JavaScript、curl 等语言的示例代码。 你的自定义模型（比如 library.book）也会出现在里面。这是查参数名最快的地方。

每次调用一个事务

每一次 JSON-2 调用都在自己的数据库事务里运行：成功就提交，出错就回滚。没有办法把多次调用放进同一个事务。这对设计集成方案有直接影响：

search_read 本身就是这个思路的例子：它在一个事务里完成搜索和读取，不会出现「搜到了、读的时候却没了」的问题。 涉及预订、付款、库存这类对一致性敏感的操作时，一定要在模块里写一个专门的方法，让外部程序只调用一次。

💡 外部调用不会触发 onchange

客户端常常想「模拟用户在表单上录入」。但直接 create() 不会执行那些只挂在表单上的 onchange 逻辑。 解决办法：在服务端尽量使用可写计算字段（第 8 章）而不是经典 onchange；或者写一个服务端方法，内部完成创建并执行需要的逻辑。

实现客户端

客户端分成两层：一层负责和 Odoo 通信（LibraryAPI 类），一层负责命令行交互（library.py）。这样以后换一种通信方式，界面代码不用动：

通信层：JSON-2 实现

import os

import requests


class LibraryAPI:
    """通过 Odoo JSON-2 API 访问 library.book 模型。"""

    def __init__(self, url, db, api_key, model="library.book"):
        self.base_url = f"{url}/json/2/{model}"
        self.session = requests.Session()
        self.session.headers.update({
            "Authorization": f"bearer {api_key}",
            "X-Odoo-Database": db,
            "User-Agent": "library-cli",
        })

    def _call(self, method, **params):
        response = self.session.post(f"{self.base_url}/{method}", json=params, timeout=30)
        if not response.ok:
            # 把 Odoo 返回的错误信息展示出来，而不是只说「400 Bad Request」
            try:
                message = response.json()["message"]
            except ValueError:
                message = response.text
            raise RuntimeError(f"Odoo error {response.status_code}: {message}")
        return response.json()

    def search_read(self, title=None):
        domain = [("name", "ilike", title)] if title else []
        return self._call("search_read", domain=domain, fields=["id", "name"])

    def create(self, title):
        ids = self._call("create", vals_list=[{"name": title}])
        return ids[0]

    def write(self, book_id, title):
        return self._call("write", ids=[book_id], vals={"name": title})

    def unlink(self, book_id):
        return self._call("unlink", ids=[book_id])


if __name__ == "__main__":
    # 直接运行这个文件时做个快速测试
    from pprint import pprint
    api = LibraryAPI(
        os.environ.get("ODOO_URL", "http://localhost:8069"),
        os.environ.get("ODOO_DB", "library"),
        os.environ["ODOO_API_KEY"],
    )
    pprint(api.search_read())
  • 用 requests.Session 复用连接和公共请求头，比每次都新建连接快。
  • _call() 是一个薄薄的包装：拼出 URL、发请求、处理错误。上层方法因此都只有一两行。
  • 出错时把 Odoo 返回的 message 提取出来抛出，命令行上就能看到真正的原因（比如「没有权限」或校验失败的提示）。
$ python3 library_json2.py
[{'id': 1, 'name': 'Odoo Development Essentials 11'},
 {'id': 2, 'name': 'Odoo 11 Development Cookbook'},
 {'id': 3, 'name': 'Brave New World'}]

界面层：命令行

用 Python 自带的 argparse 解析命令行参数，不引入其他依赖：

#!/usr/bin/env python3
import os
from argparse import ArgumentParser

from library_json2 import LibraryAPI
# from library_xmlrpc import LibraryAPI   # 旧协议的实现，接口相同


parser = ArgumentParser(description="Library book catalog client")
parser.add_argument("command", choices=["list", "add", "set", "del"])
parser.add_argument("params", nargs="*")  # 可选的附加参数
args = parser.parse_args()

api = LibraryAPI(
    os.environ.get("ODOO_URL", "http://localhost:8069"),
    os.environ.get("ODOO_DB", "library"),
    os.environ["ODOO_API_KEY"],
)

if args.command == "list":
    title = args.params[0] if args.params else None
    for book in api.search_read(title):
        print("%(id)d %(name)s" % book)

elif args.command == "add":
    title = args.params[0]
    book_id = api.create(title)
    print(f"Book added with ID {book_id} for title {title}.")

elif args.command == "set":
    if len(args.params) != 2:
        print("set command requires an ID and a Title.")
    else:
        book_id, title = int(args.params[0]), args.params[1]
        api.write(book_id, title)
        print(f"Title of Book ID {book_id} set to {title}.")

elif args.command == "del":
    book_id = int(args.params[0])
    api.unlink(book_id)
    print(f"Book with ID {book_id} was deleted.")
  • args.command 是命令，args.params 是后面的附加参数列表。命令不对时，argparse 会自动提示用法。
  • 连接信息从环境变量读取，不要硬编码在代码里（尤其是密钥）。
💡 让它像普通命令一样运行

在 Linux 上执行 chmod +x library.py，因为第一行写了 #!/usr/bin/env python3，之后就可以直接 ./library.py list。

这个程序很朴素，改进的方向很多（分页、更好的错误提示、显示作者……），但它已经完整展示了一个外部程序用 Odoo 作后端的全部要素。 另外别忘了：它受 API Key 所属用户的权限约束。如果用一个只有「图书馆用户」权限的账号的密钥，del 命令会失败 —— 第 3 章规定只有经理能删除书。

旧协议：XML-RPC 与 JSON-RPC

你会在大量现有的集成代码、文章和老版本文档里遇到 XML-RPC。它在 Odoo 20 上仍然能用，所以有必要看懂它，并知道怎么迁移。

XML-RPC 的用法

>>> from xmlrpc import client
>>> srv = "http://localhost:8069"
>>> common = client.ServerProxy(f"{srv}/xmlrpc/2/common")
>>> common.version()
{'server_version': '20.0', 'server_version_info': [20, 0, 0, 'final', 0, ''], ...}

>>> db, user, password = "library", "admin", "admin"    # password 也可以是 API Key
>>> uid = common.authenticate(db, user, password, {})
>>> uid
2

>>> api = client.ServerProxy(f"{srv}/xmlrpc/2/object")
>>> api.execute_kw(db, uid, password, "res.users", "search_count", [[]])
5
>>> api.execute_kw(db, uid, password, "res.users", "search_read",
...                [[("login", "=", "admin")], ["login", "name"]])
[{'id': 2, 'login': 'admin', 'name': 'Mitchell Admin'}]
>>> # 也可以用关键字参数（第 7 个参数）
>>> api.execute_kw(db, uid, password, "res.users", "search_read", [],
...                {"domain": [("login", "=", "admin")], "fields": ["login", "name"]})
  • /xmlrpc/2/common 提供不需要登录的公共方法：version() 查版本，authenticate(db, login, password, {}) 校验账号并返回用户 ID（失败返回 False）。
  • /xmlrpc/2/object 的 execute_kw 调用模型方法，参数依次是：数据库名、用户 ID、密码（或 API Key）、模型、方法、位置参数列表、可选的关键字参数字典。
  • 它是无状态的：每次调用都要带上数据库、用户和密码。
  • XML-RPC 协议本身不支持 None 值。这就是 Odoo 惯例让方法「至少返回 True」的历史原因。

对应的 LibraryAPI 实现（和 JSON-2 版本接口完全相同）：

import xmlrpc.client


class LibraryAPI:
    def __init__(self, url, db, api_key, model="library.book", login="admin"):
        common = xmlrpc.client.ServerProxy(f"{url}/xmlrpc/2/common")
        self.api = xmlrpc.client.ServerProxy(f"{url}/xmlrpc/2/object")
        self.uid = common.authenticate(db, login, api_key, {})
        self.pwd = api_key
        self.db = db
        self.model = model

    def _execute(self, method, arg_list, kwarg_dict=None):
        return self.api.execute_kw(
            self.db, self.uid, self.pwd, self.model,
            method, arg_list, kwarg_dict or {})

    def search_read(self, title=None):
        domain = [("name", "ilike", title)] if title else []
        return self._execute("search_read", [domain, ["id", "name"]])

    def create(self, title):
        return self._execute("create", [{"name": title}])

    def write(self, book_id, title):
        return self._execute("write", [[book_id], {"name": title}])

    def unlink(self, book_id):
        return self._execute("unlink", [[book_id]])

从 XML-RPC 迁移到 JSON-2

XML-RPC / JSON-RPCJSON-2
common.version()GET /web/version
common.authenticate() 拿 uid，之后每次带 db、uid、密码不需要登录。每次请求带 Authorization: bearer <API Key>；多库时加 X-Odoo-Database
execute_kw(db, uid, pwd, 模型, 方法, args, kwargs)POST /json/2/模型/方法，请求体是一个 JSON 对象
记录 ID 放在 args 的第一个位置记录 ID 放在 "ids" 键里
位置参数 + 关键字参数只有命名参数
上下文放在 kwargs 的 context 里上下文放在请求体的 "context" 键里
需要用户 ID 时直接用 authenticate 的返回值调用 res.users/context_get，返回值里有 uid
db 服务（建库、备份……）Odoo 20 已移除。改用 /web/database/* HTTP 端点，或服务器上的 odoo db 命令（第 2 章）
ⓘ OdooRPC 库

原书第二个客户端用的是 OCA 维护的 OdooRPC 库，它提供了模仿服务端写法的 env["library.book"].search_read(...) 风格的客户端 API。 但它底层走的是 /jsonrpc，同样属于被废弃的端点。在它支持 JSON-2 之前，新项目建议像本章这样直接用 requests 调用 JSON-2 —— 代码量也没有多多少。

💡 暂时没法迁移？

旧端点每次被调用都会在服务器日志里打印一条废弃警告。迁移完成之前，可以按警告里的提示用 --log-handler=odoo.addons.rpc.controllers:ERROR 屏蔽它们，但别忘了：Odoo 22 会彻底移除这些端点。

小结

  • Odoo 的外部 API 能调用任意模型的公开方法；外部程序以 API Key 所属用户的身份和权限运行。
  • Odoo 19+ 的 JSON-2 API：POST /json/2/模型/方法，Authorization: bearer 认证，请求体里用命名参数，ids 和 context 是特殊键。
  • 读数据首选 search_read；记录集在外部表现为 ID 列表，多对一字段为 [ID, 名称]。
  • 每次调用是独立的事务；需要一致性的多步操作要封装成一个服务端方法。
  • /doc 页面是当前数据库的动态 API 文档和测试台。
  • XML-RPC / JSON-RPC 已废弃、计划在 Odoo 22 移除；看得懂它，但新代码用 JSON-2。
  • 把通信层和界面层分开，换协议时只改一行 import。
