第 17 章

开发环境进阶：Docker 与断点调试

第 2 章我们在 Ubuntu 上从源码安装了 Odoo。这种方式最透明，但对用 Windows 或 macOS 的同学门槛不低，换一台电脑又要从头装一遍。 这一章介绍另一条路：用 Docker 一条命令把 Odoo 20 和 PostgreSQL 都跑起来。 然后再解决第 8 章留下的一个问题：在终端里用 pdb 调试不太直观，我们改用 VS Code 的图形化调试器，点一下就能打断点、看变量、单步执行。

本章目标

  • 理解镜像、容器、数据卷、端口映射这几个 Docker 概念
  • 用 Docker Compose 搭建 Odoo 20 + PostgreSQL 开发环境，并挂载自己的模块
  • 在容器里执行建库、安装 / 升级模块、odoo shell 等日常操作
  • 用 VS Code + debugpy 调试源码安装的 Odoo（第 2 章的环境）
  • 用 VS Code 附加到 Docker 容器里的 Odoo 进行调试
  • 熟练使用断点、条件断点、单步执行、调试控制台

为什么用 Docker

Odoo 的运行需要好几样东西：特定版本的 Python、几十个 Python 库、一些系统库、PostgreSQL 数据库、生成 PDF 用的 wkhtmltopdf…… 第 2 章我们一样一样装上了它们。Docker 的思路是：把「Odoo 加上它需要的一切」提前打包成一个镜像， 任何装了 Docker 的电脑都能直接运行它，不用关心本机是什么系统。

镜像（image）
一个只读的软件包，里面是一套完整的运行环境。Odoo 官方在 Docker Hub 上发布了 odoo:20 镜像，PostgreSQL 也有官方的 postgres:17 镜像。
容器（container）
镜像运行起来的实例，像一台轻量的虚拟机。同一个镜像可以启动很多个容器。容器删掉后，里面的改动也就没了。
数据卷（volume）
容器外面的持久存储。数据库文件、附件这些不能丢的数据放在卷里，删掉容器再重建，数据还在。
挂载（bind mount）
把本机的一个目录「映射」进容器。我们把自己的模块目录挂载进去：在本机用编辑器改代码，容器里立刻就能看到。
端口映射
把容器里的端口暴露到本机。容器里 Odoo 监听 8069，映射后在本机浏览器访问 localhost:8069 即可。
源码安装（第 2 章）Docker（本章）
适合的系统Linux（Windows 上用 WSL）任何装了 Docker 的系统
安装耗时装系统包、建虚拟环境、装依赖，二三十分钟下载镜像，几分钟
Odoo 源码就在 ~/work20/odoo，随时可以看、可以改在镜像里，要看需要先复制出来
切换版本再克隆一份、再建一个虚拟环境把 odoo:20 改成 odoo:19 即可
团队一致性每个人的环境多少有差异所有人用同一个镜像，「在我电脑上能跑」的问题少很多
ⓘ 两种方式不冲突

很多开发者两种都用：日常开发用 Docker，需要深入阅读或修改 Odoo 核心代码时用源码安装。本章后半部分的 VS Code 调试，两种环境都会讲到。

安装 Docker

  • Windows / macOS：安装 Docker Desktop（docker.com 下载）。Windows 上它会使用 WSL 2 作为后端，安装向导会提示你启用。
  • Ubuntu：可以安装 Docker 官方的 Docker Engine，也可以直接用系统自带的软件包：
sudo apt install -y docker.io docker-compose-v2
sudo usermod -aG docker $USER      # 让当前用户不用 sudo 也能运行 docker
# 注销并重新登录，让用户组的变化生效

装好后检查一下：

docker --version
docker compose version
docker run --rm hello-world        # 能打印出 "Hello from Docker!" 就说明一切正常
注意是 docker compose，不是 docker-compose

Compose 现在是 Docker 的一个子命令（V2），写作 docker compose，中间是空格。网上的老教程常写成带连字符的 docker-compose，那是已经停止维护的 V1 版本。

用 Docker Compose 搭环境

一个 Odoo 环境需要两个容器，还要配置挂载、端口和数据卷。如果都写在 docker run 命令行里，会长得没法看。 Docker Compose 让我们把这些写进一个 YAML 文件，然后一条命令全部启动。先建一个项目目录： 

mkdir -p ~/odoo20-docker/config ~/odoo20-docker/addons
cd ~/odoo20-docker
# 把前面章节写好的模块复制进来（没有的话先空着）
cp -r ~/work20/library/* addons/

compose.yaml

services:
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: odoo
      POSTGRES_PASSWORD: odoo
    volumes:
      - db-data:/var/lib/postgresql/data

  odoo:
    image: odoo:20
    depends_on:
      - db
    ports:
      - "8069:8069"
    environment:
      PGHOST: db              # 数据库的主机名，就是上面的服务名
      PGPORT: 5432
      PGUSER: odoo
      PGPASSWORD: odoo
      ODOO_DEV: all           # 相当于 --dev=all
    volumes:
      - ./addons:/mnt/extra-addons
      - ./config:/etc/odoo
      - odoo-data:/var/lib/odoo

volumes:
  db-data:
  odoo-data:

逐段看一下：

  • services 下面定义了两个服务 db 和 odoo。Compose 会给它们建一个专用网络，容器之间可以用服务名当主机名互相访问，所以 Odoo 连接数据库时主机名写 db。
  • POSTGRES_USER / POSTGRES_PASSWORD 让 PostgreSQL 镜像在第一次启动时创建一个名为 odoo 的数据库用户。别用 postgres，Odoo 会拒绝用这个用户连接（附录 B）。
  • PGHOST、PGPORT、PGUSER、PGPASSWORD 是 PostgreSQL 的标准环境变量，Odoo 20 会直接读取它们作为数据库连接参数。ODOO_DEV 对应 --dev 选项。 四个 PG* 变量最好都写上：官方镜像的启动脚本发现缺了哪一个，就会自己往命令行后面追加 --db_port 之类的参数，而 odoo db 这样的子命令不接受追加在后面的这些参数。
  • volumes 里以 ./ 开头的是挂载本机目录，其余的是命名数据卷，在文件末尾声明。
⇪ 用环境变量配置 Odoo

Odoo 20 的大部分配置项都能用环境变量设置，优先级是：命令行 > 环境变量 > 配置文件 > 默认值。 数据库连接用 PostgreSQL 的标准变量（PGHOST、PGPORT、PGUSER、PGPASSWORD、PGDATABASE）， 配置文件路径用 ODOO_RC，开发选项用 ODOO_DEV。这在容器里特别方便：同一个镜像，换一组环境变量就是另一套配置。

config/odoo.conf

挂载 ./config 会替换掉镜像自带的配置文件，所以我们要自己写一个：

[options]
addons_path = /mnt/extra-addons
data_dir = /var/lib/odoo
http_interface = 0.0.0.0
admin_passwd = 换成一个你自己的主密码

addons_path 只需要写我们挂载的目录，Odoo 自带的模块路径会自动加上。注意这里写的都是容器里的路径，不是本机路径。 http_interface = 0.0.0.0 不能省：Odoo 20 默认只监听 127.0.0.1，在容器里这意味着只有容器自己能访问，端口映射过来的请求进不去，浏览器会一直连不上。

启动

docker compose up -d          # 后台启动两个容器（第一次会先下载镜像）
docker compose ps             # 查看容器状态
docker compose logs -f odoo   # 实时查看 Odoo 的日志，Ctrl+C 退出查看（容器继续运行）

日志里出现 HTTP service running on 0.0.0.0:8069 之后，打开浏览器访问 http://localhost:8069，就能看到第 2 章介绍过的数据库管理页面。

日常操作

在容器里执行命令用 docker compose exec 服务名 命令。容器里的 odoo 命令和第 2 章源码安装的完全一样， 而且因为配置文件路径（ODOO_RC）和数据库连接（PG* 变量）都已经通过环境变量设好了，不用再写 -c： 

# 建一个带演示数据、默认语言为简体中文的数据库
docker compose exec odoo odoo db init library --with-demo --language zh_CN

# 安装 / 升级模块
docker compose exec odoo odoo module install -d library library_app
docker compose exec odoo odoo module upgrade -d library library_app

# 进入 odoo shell（第 7 章）
docker compose exec odoo odoo shell -d library

# 重启 Odoo（改了清单、或者需要重新加载 Python 代码时）
docker compose restart odoo
命令作用
docker compose up -d创建并启动所有容器（已存在就直接启动）
docker compose stop停止容器，下次 up -d 或 start 继续用
docker compose down停止并删除容器，数据卷保留
docker compose down -v连数据卷一起删除——所有数据库都没了，相当于从零开始
docker compose logs -f odoo跟踪 Odoo 的日志
docker compose exec odoo bash在 Odoo 容器里开一个终端，四处看看
docker compose pull && docker compose up -d拉取最新的镜像（包含 Odoo 的每日修复）并重建容器
💡 想看 Odoo 源码？从容器里复制一份出来

镜像里的 Odoo 是用官方的 Debian 软件包安装的，源码在 /usr/lib/python3/dist-packages/odoo。复制到本机，就能在编辑器里搜索和阅读，后面调试时也用得上： 

docker compose cp odoo:/usr/lib/python3/dist-packages/odoo ./odoo-src
这是开发环境，不是生产环境

本章的配置为了方便开发，密码写死在文件里、打开了 --dev。生产部署请参照第 15 章的安全要求（强主密码、关闭数据库管理器、反向代理与 HTTPS 等）， 无论最后是否使用容器。

图形化调试器是怎么工作的

第 8 章我们用 breakpoint() 在终端里调试。它能用，但要记一堆单字母命令，看复杂的数据结构也费劲。 VS Code 的调试器把这一切变成了图形界面：在行号左边点一下就是断点，变量的值直接在侧边栏里展开。

VS Code 本身并不执行你的代码。它通过一个叫 debugpy 的 Python 库来控制 Odoo 进程：debugpy 运行在 Odoo 进程内部， 在一个网络端口上等待指令；VS Code 连上这个端口，发出「在第 42 行停下」「执行下一行」「告诉我变量 x 的值」这样的请求。

VS Code 有两种开始调试的方式，后面两节各用一种：

  • launch（启动）：由 VS Code 来启动 Odoo，自动带上 debugpy。适合源码安装的环境。
  • attach（附加）：Odoo 自己带着 debugpy 先跑起来，VS Code 再连上去。适合 Docker 或远程服务器。

两种方式都要先在 VS Code 里安装微软的 Python 扩展（它会一并装上 Python Debugger 扩展）。 所有调试配置都写在项目的 .vscode/launch.json 文件里。

调试源码安装的 Odoo（launch）

用 VS Code 打开第 2 章的工作目录 ~/work20（菜单「文件 → 打开文件夹」）。Windows 用户如果在 WSL 里安装了 Odoo， 先装 VS Code 的 WSL 扩展，再用「连接到 WSL」打开这个目录，后面的步骤完全一样。然后新建 .vscode/launch.json： 

{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Odoo 20：library 库",
            "type": "debugpy",
            "request": "launch",
            "python": "${workspaceFolder}/env20/bin/python",
            "program": "${workspaceFolder}/odoo/odoo-bin",
            "args": [
                "-c", "${workspaceFolder}/library.conf",
                "-d", "library",
                "--dev=xml,qweb,access"
            ],
            "console": "integratedTerminal",
            "justMyCode": false
        }
    ]
}
type
debugpy 表示用 Python Debugger 扩展。
python
用哪个 Python 解释器运行。一定要指向虚拟环境里的那个，否则会找不到 Odoo 的依赖库。
program / args
相当于在终端里执行 odoo-bin -c library.conf -d library --dev=...。${workspaceFolder} 是打开的文件夹路径。
justMyCode
默认是 true，调试器只在「你的代码」里停，单步时会跳过库代码。设成 false 才能单步进入 Odoo 自己的源码（比如 ORM 的 write()），对学习非常有帮助。
调试时不要用 --dev=reload，也不要开多进程

reload 检测到文件变化时会重新启动整个进程，调试会话随之断开，所以上面的配置只开了 xml,qweb,access。 改了 Python 代码后，按调试工具栏上的「重启」按钮（Ctrl+Shift+F5）即可。另外，配置文件里的 workers 必须是 0（默认值）： 多进程模式下请求由子进程处理，调试器默认只附加在主进程上，断点不会生效。

保存后，切换到 VS Code 左侧的「运行和调试」面板，在顶部的下拉框里选中「Odoo 20：library 库」，按 F5。Odoo 会在 VS Code 的集成终端里启动，日志和平时一样。

调试 Docker 里的 Odoo（attach）

容器里的 Odoo 不是 VS Code 启动的，所以要换个思路，分三步：

  1. 在镜像里装上 debugpy；
  2. 让 Odoo 在 debugpy 的「监听」下启动，并把调试端口映射出来；
  3. VS Code 用 attach 方式连上这个端口，并告诉它容器里的路径和本机路径怎么对应。

第一步：给镜像加上 debugpy

官方镜像里没有 debugpy。在项目目录新建一个 Dockerfile.debug，在官方镜像的基础上装上它：

FROM odoo:20
USER root
RUN pip3 install --no-cache-dir --break-system-packages debugpy
USER odoo

镜像基于 Ubuntu 24.04，系统的 Python 默认不允许直接用 pip 安装包（为了保护系统软件包），--break-system-packages 表示我们知道自己在做什么。 装完切回 odoo 用户，和官方镜像保持一致。

第二步：调试用的 Compose 覆盖文件

我们不改 compose.yaml，而是另写一个只包含「差异」的覆盖文件。需要调试时把两个文件叠加起来使用，平时还是只用原来那个： 

services:
  odoo:
    build:
      context: .
      dockerfile: Dockerfile.debug
    environment:
      ODOO_DEV: xml,qweb,access      # 调试时不要 reload
    command:
      - python3
      - -m
      - debugpy
      - --listen
      - 0.0.0.0:5678
      - /usr/bin/odoo
    ports:
      - "127.0.0.1:5678:5678"        # 只允许本机连接调试端口

docker compose -f compose.yaml -f compose.debug.yaml up -d --build
  • command 把容器的启动命令换成「用 debugpy 运行 /usr/bin/odoo」。--listen 0.0.0.0:5678 让 debugpy 在容器的 5678 端口等待 VS Code 连接。
  • 端口映射写成 127.0.0.1:5678:5678，只绑定本机地址。调试端口能执行任意代码，绝不能暴露到网络上。
  • 覆盖文件里的 environment、ports 会和 compose.yaml 里的合并：ODOO_DEV 被覆盖，8069 端口照样保留。

第三步：attach 配置与路径映射

容器里的文件路径和本机不一样：本机的 ./addons/library_app/models/library_book.py，在容器里是 /mnt/extra-addons/library_app/models/library_book.py。 VS Code 在本机文件上设的断点，必须翻译成容器里的路径，debugpy 才认得。这就是 pathMappings 的作用： 

{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "附加到 Docker 里的 Odoo",
            "type": "debugpy",
            "request": "attach",
            "connect": { "host": "localhost", "port": 5678 },
            "pathMappings": [
                {
                    "localRoot": "${workspaceFolder}/addons",
                    "remoteRoot": "/mnt/extra-addons"
                },
                {
                    "localRoot": "${workspaceFolder}/odoo-src",
                    "remoteRoot": "/usr/lib/python3/dist-packages/odoo"
                }
            ],
            "justMyCode": false
        }
    ]
}

第二条映射是可选的：如果你按前面的提示把 Odoo 源码复制到了 ./odoo-src，单步进入 Odoo 核心代码时 VS Code 就能打开对应的文件。 用 VS Code 打开 ~/odoo20-docker 目录，选中「附加到 Docker 里的 Odoo」，按 F5。底部状态栏变色，说明已经连上了。

ⓘ 断开调试器，Odoo 照常运行

attach 模式下，停止调试（Shift+F5）只是断开连接，容器里的 Odoo 继续运行；再按 F5 可以随时重新连上。 调试结束后，用 docker compose up -d（不带 compose.debug.yaml）回到普通模式。

使用调试器

两种方式连上之后，用法就完全一样了。拿第 3 章图书模型的「检查 ISBN」按钮试一试：

  1. 在 VS Code 里打开 library_app/models/library_book.py，在 button_check_isbn 方法第一行的行号左边点一下，出现一个红点，这就是断点。
  2. 在浏览器里打开一本书，点「Check ISBN」按钮。浏览器会一直转圈——因为服务器停在了断点上。
  3. VS Code 自动跳到前台，断点所在行高亮显示。现在可以四处看看了。
区域 / 按键用途
变量面板当前作用域里的所有变量。记录集可以展开，看到每个字段的值。
监视面板添加任意表达式（比如 len(self)、book.state），每走一步自动刷新。
调用栈面板是谁一层层调用到这里的。点上面的某一层，可以看到那一层当时的变量——想知道「Odoo 是怎么调到我的方法的」，就看这里。
调试控制台在当前位置执行任意 Python 表达式，甚至调用 ORM：self.env['res.partner'].search_count([])。
F5 继续一直运行到下一个断点（没有的话请求就正常完成了）。
F10 单步跳过执行当前行，不进入它调用的函数。
F11 单步进入进入当前行调用的函数内部。配合 justMyCode: false，能一路走进 Odoo 的 ORM。
Shift+F11 单步跳出执行完当前函数，回到调用它的地方。

条件断点与日志点

断点打在一个会被调用很多次的地方（比如计算方法）时，每次都停下来会很烦。在红点上右键 → 编辑断点，可以设置：

  • 条件：只有表达式为真时才停，比如 book.id == 3 或 not book.isbn。
  • 命中次数：第 N 次经过时才停。
  • 日志消息（logpoint）：不停下来，只把一段文字打印到调试控制台，花括号里可以写表达式，比如 检查 {book.name}。相当于不用改代码的 print。

💡 用调试器读懂 Odoo

调试器不只是用来修 bug 的。想知道「点保存时 Odoo 到底做了什么」？在 write() 的重写方法里打一个断点，用 F11 一路走进 ORM，看它怎样检查权限、触发计算字段、写入数据库。 这比读文档直观得多，也是很多资深 Odoo 开发者学习新功能的方式。

小结

  • Docker 把 Odoo 和它的依赖打包成镜像；容器是镜像的运行实例；数据放在数据卷里，代码通过挂载进入容器。
  • compose.yaml 定义 db 和 odoo 两个服务；容器间用服务名互访；PGHOST、PGUSER、PGPASSWORD、ODOO_DEV 等环境变量直接配置 Odoo。
  • 日常命令：docker compose up -d、logs -f、exec odoo odoo ...、restart odoo；down -v 会删光数据，慎用。
  • VS Code 调试 = 界面（VS Code）+ 执行者（Odoo 进程里的 debugpy），配置写在 .vscode/launch.json。
  • 源码安装用 launch，Docker 用 attach + pathMappings；调试端口只绑定 127.0.0.1。
  • 调试时不要开 --dev=reload，workers 保持为 0；justMyCode: false 才能进入 Odoo 源码。
  • 条件断点、日志点、调试控制台能大大减少「加 print → 重启 → 再看」的循环。
