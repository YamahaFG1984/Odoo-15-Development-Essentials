第 19 章

编码规范与工具链

到这里，你已经能写出可以运行的 Odoo 模块了。但「能跑」和「能交付」之间还隔着一段路：同事要能读懂，半年后的你要能改动， 客户的系统要能平稳升级，提交给 OCA 的代码要能通过审核。这一章介绍 Odoo 社区通用的编码规范， 以及一套能在每次提交前自动检查代码的工具链。规范大多是约定，没有对错之分，但遵守大家都在用的那一套，能省掉无数沟通成本。

本章目标

  • 按约定组织模块目录，给文件、模型、XML ID、方法起名
  • 按推荐的顺序排列模型类的内容，写出风格一致的 Python 和 XML
  • 理解清单版本号的含义，用迁移脚本处理数据结构的变化
  • 用 ruff、pylint-odoo、prettier 检查和格式化代码，用 pre-commit 在提交前自动运行
  • 用 Odoo 约定的格式写 Git 提交信息，按 Odoo 版本组织分支

规范来自哪里

Odoo 世界里有两套被广泛参考的规范，它们大部分是一致的：

📘

Odoo 官方编码规范

Odoo 官方文档「Coding guidelines」一节，规定了官方模块的目录结构、命名和代码风格。Odoo 源码根目录下还有一个 ruff.toml，就是官方使用的检查规则。

🤝

OCA 规范

OCA 在官方规范的基础上增加了清单、版本号、README 等要求，并把它们做成了一套自动化工具（模板仓库 + pre-commit 配置），所有 OCA 仓库统一使用。

本章以官方规范为主线，在 OCA 有额外要求的地方单独说明。如果你的代码不打算开源，OCA 的额外要求可以按需采用，但工具链本身同样值得用起来。

XML ID 的命名

XML ID 一旦发布就不应该再改（别的模块可能引用了它），所以从一开始就按约定起名很重要。官方规范是以模型名开头：

记录类型格式例子
视图<模型>_view_<类型>library_book_view_form、library_book_view_list
继承视图<被继承的视图>_inherit_<当前模块>view_partner_form_inherit_library_app
窗口动作<模型>_action，其他的加后缀library_book_action、library_book_action_borrowed
菜单<模型>_menu；顶级菜单 <模块>_menu_rootlibrary_book_menu、library_app_menu_root

ⓘ 本教程的写法

为了和原书保持一致，前面章节用的是 view_form_book、action_library_book 这样的名字。它们完全能用，只是不符合官方的推荐格式。 新项目建议直接采用上表的约定；已经上线的模块则不要为了改名而改名——改 XML ID 会让 Odoo 删掉旧记录、新建一条，引用旧 ID 的地方都会出错。

Python 的约定

模型类内部的顺序

一个模型类往往有几十个字段、几十个方法。按固定的顺序排列，读代码的人就知道去哪里找：

命名

对象约定
多对一字段以 _id 结尾：publisher_id
一对多、多对多字段以 _ids 结尾：author_ids、line_ids
计算 / 反写 / 搜索方法_compute_<字段>、_inverse_<字段>、_search_<字段>
默认值 / 选择项方法_default_<字段>、_selection_<字段>
onchange / 约束方法_onchange_<字段>、_check_<名字>
按钮调用的方法action_<做什么>：action_confirm、action_done（原书用的 button_ 前缀也能用，但官方模块统一用 action_）
只在内部使用的方法以下划线开头：_check_isbn。下划线开头的方法不能通过外部 API 调用
变量记录集按模型起名：partner、partners；只有存 ID 的变量才用 _id / _ids 结尾。别把一个伙伴记录存进叫 partner_id 的变量

几条重要的习惯

  • 导入顺序：标准库 → 第三方库 → odoo → odoo.addons → 本模块的相对导入，每组之间空一行。工具会自动帮你排好。
  • 用日志代替 print：在文件顶部 _logger = logging.getLogger(__name__)，然后 _logger.info("Checked %s books", count)。参数用逗号传，不要用 f-string 先拼好——日志级别不够时，拼接的开销就白费了。
  • 不要自己 commit：self.env.cr.commit() 会打破 Odoo 的事务管理，出错时无法回滚。只有在极少数场合（比如需要分批提交的长任务）才这样做，并加注释说明原因。
  • 少写 SQL：优先用 ORM。必须写 SQL 时用 odoo.tools.SQL 组装，绝不用字符串拼接或 % 格式化把变量放进 SQL，那是 SQL 注入漏洞。
  • 谨慎使用 sudo()：只在确实需要越过权限的那一小段代码里用，并且尽量缩小它影响的范围。
  • 重写方法要调用 super()，并返回它的结果（附录 B）。

XML 的约定

<?xml version="1.0" encoding="utf-8"?>
<odoo>
    <record id="library_book_view_form" model="ir.ui.view">
        <field name="name">library.book.view.form</field>
        <field name="model">library.book</field>
        <field name="arch" type="xml">
            <form>
                ...
            </form>
        </field>
    </record>
</odoo>
  • 用 4 个空格缩进；<record> 的属性先写 id 再写 model。
  • 视图的 name 字段用模型名加视图类型，点号分隔：library.book.view.form。继承视图的 name 加上 .inherit.<模块>。
  • 菜单可以用 <menuitem> 快捷标签，其他记录一律用 <record>。
  • 继承视图时，能用 <field name="x" position="after"> 定位的就不用 XPath；必须用 XPath 时，尽量用 name 属性定位，而不是 //group[2] 这种依赖位置的写法——父视图一调整顺序，按位置定位就会出错。
  • 不要用 position="replace" 删掉别人视图里的元素，改用 position="attributes" 设置 invisible="1"。删掉的元素可能正被别的模块的继承视图引用。

版本号的五段含义

版本号不只是给人看的。升级模块时，Odoo 会比较数据库里记录的版本和清单里的新版本， 如果新版本更高，就运行模块 migrations/ 目录里对应版本的迁移脚本。所以：每次发布都要递增版本号，尤其是改了数据结构的时候。

迁移脚本

大部分改动 Odoo 都能自动处理：加字段就加列，改视图就更新视图。但有些改动 Odoo 无法猜到你的意图，比如字段改名—— ORM 只会看到「旧字段没了、多了个新字段」，于是新建一个空列，旧数据就丢了。这时需要迁移脚本：

假设 1.1.0 版把图书的 date_published 字段改名为 published_on，并且新增了一个由 ISBN 规范化而来的字段。目录结构：

library_app/
└── migrations/
    └── 20.0.1.1.0/
        ├── pre-migrate.py
        └── post-migrate.py

from odoo.tools.sql import column_exists, rename_column


def migrate(cr, version):
    # 在 ORM 创建新列之前，把旧列改名，数据原样保留
    if column_exists(cr, "library_book", "date_published"):
        rename_column(cr, "library_book", "date_published", "published_on")

from odoo import SUPERUSER_ID
from odoo.api import Environment


def migrate(cr, version):
    env = Environment(cr, SUPERUSER_ID, {})
    books = env["library.book"].search([("isbn", "!=", False)])
    for book in books:
        book.isbn_normalized = book.isbn.replace("-", "")
  • 函数名必须是 migrate，参数是游标和升级前的版本号。全新安装时不会执行迁移脚本。
  • 文件名必须以 pre-、post- 或 end- 开头，后面的部分随意。
  • pre 阶段只能用 SQL（模型还是旧的）；post 阶段可以像上面那样建一个环境，用 ORM 操作数据。
  • 迁移脚本要能重复执行而不出错（比如先检查列是否存在），万一升级中途失败需要重跑。
💡 先在预发布环境演练

迁移脚本出错的代价是生产数据。上线前，一定用生产库的副本（第 15 章的 odoo db duplicate --neutralize）完整跑一遍升级。

工具链：让机器检查规范

规范靠人记是记不住的。下面这些工具能自动发现问题，大部分还能自动修复：

工具检查什么例子
ruffPython 代码风格和常见错误，并能自动格式化。速度极快，取代了 flake8、isort、black 等一堆老工具未使用的导入、导入顺序、行太长、可疑的写法

pre-commit：每次提交前自动运行

工具有了，还得记得运行。pre-commit 是一个 Git 钩子管理器：每次 git commit 时，它自动对这次要提交的文件运行配置好的检查， 有问题就拒绝提交。所有工具的版本都写在配置文件里，团队里每个人用的是完全相同的检查。

在仓库根目录新建 .pre-commit-config.yaml。下面是一个适合个人或小团队的精简配置，各工具的版本取自 OCA 模板中 Odoo 20 对应的版本：

repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v6.0.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-xml
      - id: check-merge-conflict
      - id: debug-statements        # 拦住忘了删的 breakpoint()

  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.16.8
    hooks:
      - id: ruff-check
        args: [--fix, --exit-non-zero-on-fix]
      - id: ruff-format

  - repo: https://github.com/OCA/pylint-odoo
    rev: v10.0.11
    hooks:
      - id: pylint_odoo
        args: [--rcfile=.pylintrc]

[MASTER]
load-plugins=pylint_odoo
score=n

[ODOOLINT]
valid-odoo-versions=20.0
manifest-required-keys=license

[MESSAGES CONTROL]
disable=all
enable=sql-injection,
    print-used,
    method-required-super,
    method-compute,
    method-inverse,
    method-search,
    manifest-version-format,
    manifest-required-key,
    translation-required,
    attribute-deprecated,
    eval-used,
    dangerous-default-value

然后安装并启用：

(env20) $ pip install pre-commit
(env20) $ pre-commit install            # 在当前仓库安装 Git 钩子（每个仓库做一次）
(env20) $ pre-commit run --all-files    # 第一次对所有文件跑一遍

第一次运行会下载各个工具，稍慢；以后每次 git commit 都会自动执行。

ⓘ 想要和 OCA 完全一致？

OCA 用一个 copier 模板生成所有仓库的配置文件（pre-commit、ruff、pylint、prettier、eslint、GitHub Actions 等）。 你的项目也可以直接用它：pip install copier，然后 copier copy https://github.com/OCA/oca-addons-repo-template.git 你的仓库目录，按提示回答几个问题（Odoo 版本选 20.0）。 以后模板更新了，运行 copier update 就能同步。

Git：分支与提交信息

仓库与分支

Odoo 社区的惯例是：一个 Git 仓库放一组相关的模块（仓库本身就是一个 addons 目录，可以直接加进 addons_path）， 并且每个 Odoo 大版本一个长期分支，分支名就是版本号：

提交信息

Odoo 和 OCA 用同一种格式：第一行是 [标签] 模块名: 简短描述，空一行后写详细说明（为什么改、怎么改的）。

[ADD] library_app: book catalog PDF report

Librarians need a printable list of the books on a shelf.
The report groups books by publisher and shows the authors.
标签含义标签含义
[ADD]新增模块或功能[FIX]修复 bug
[IMP]改进已有功能[REF]重构，功能不变
[REM]删除功能或代码[MOV]移动文件或代码
[I18N]翻译相关[PERF]性能优化
[CLN]清理代码[LINT]修正代码检查问题
[REV]撤销之前的提交[MIG]把模块迁移到新的 Odoo 版本（OCA 常用）
  • 第一行尽量不超过 50 个字符，用英文写，描述「做了什么」，而不是「改了哪个文件」。
  • 一个提交只做一件事。修 bug 和重构混在一个提交里，回头查问题时会很痛苦。
  • 这样的历史记录可以直接用 git log --oneline 当作更新日志来读。

小结

  • 参照 Odoo 官方编码规范和 OCA 规范；它们大体一致，OCA 多了清单、版本号和工具链的要求。
  • 文件按模型命名：library_book.py、library_book_views.xml；XML ID 以模型名开头：library_book_view_form、library_book_action。
  • 模型类按「属性 → 字段 → 计算与约束 → ORM 重写 → 动作 → 业务方法」的顺序排列；多对一以 _id、多对多以 _ids 结尾；按钮方法用 action_ 前缀。
  • 版本号 20.0.主.次.修订，每次发布都要递增；字段改名等 ORM 猜不到的变化，用 migrations/ 里的 pre / post 脚本处理。
  • ruff 管 Python 风格，pylint-odoo 管 Odoo 特有问题，prettier 管 XML 和 JS 格式；pre-commit 让它们在每次提交前自动运行。
  • 提交信息格式 [TAG] module: summary；每个 Odoo 大版本一个长期分支。

动手练习

  1. 对前面章节写的 library_app 运行 ruff check 和 ruff format --diff，看看有哪些地方不符合规范。
  2. 按本章的配置给你的模块仓库装上 pre-commit，然后故意在代码里写一行 print("debug")，尝试提交，看看会发生什么。
  3. 把 library_app 的按钮方法 button_check_isbn 改名为 action_check_isbn，别忘了同时修改视图里的按钮。这需要迁移脚本吗？为什么？
  4. 给 library.book 的某个字段改名，写一个 pre-migrate 脚本保留旧数据，递增版本号后升级，确认数据还在。
  5. 把你的模块仓库整理成「每个 Odoo 版本一个分支」的结构，并用 [ADD]、[IMP] 等标签重写最近几次提交的信息（在还没推送的分支上练习）。
